# Справочник к уроку 08. Как спроектировать нормальный Dashboard

Урок 08 показывает механику конструктора. Здесь другой вопрос: **что вообще стоит положить на Dashboard и в каком порядке**.

Dashboard полезнее воспринимать не как склад графиков, а как последовательность ответов:

```text
что происходит
→ есть ли отклонение
→ где оно
→ почему
→ какие записи за ним стоят
```

## Сначала определите задачу панели

До первого графика стоит понять:

- кто будет смотреть Dashboard;
- что человек должен увидеть в первую очередь;
- какое решение принимается по этой информации;
- какие отклонения требуют внимания;
- нужна ли после обзора детализация до отдельных записей.

Без этого компоновка быстро превращается в случайный набор виджетов.

## Верх — для ключевых показателей

На первом экране оставляйте только те KPI, которые действительно нужны для общего состояния. Если одинаково крупными сделать все доступные показатели, приоритеты исчезнут.

Пример обзорного набора:

```text
операций всего
ошибок
доля ошибок
не обработано
```

## После состояния нужна динамика

Одно итоговое число отвечает на вопрос «сколько?». Временной график добавляет второй важный вопрос — «что с этим происходило?».

Для динамики обычно подходят `Line Chart`, `Bar Chart` с временной осью или `Mixed Chart`.

## Затем покажите, где находится проблема

Здесь выбор зависит от вопроса:

```text
Bar Chart → сравнение категорий
Heatmap   → сочетание двух измерений
Treemap   → вклад многих категорий
```

Например: ошибки по участкам или тип ошибки × участок.

## Детализацию ставьте после обзора

Обычный путь чтения выглядит так:

```text
есть проблема?
↓
когда появилась?
↓
где?
↓
какого типа?
↓
какие конкретно записи?
```

Поэтому большая `Table` чаще полезнее после обзорных графиков, а не первой на экране.

## Один график — один основной вопрос

Перед добавлением Chart попробуйте сформулировать его назначение одной фразой:

> Как меняется количество ошибок по дням?

или:

> На каком участке больше всего ошибок?

Если один график одновременно пытается показать объём, процент, план, факт, среднее, структуру и динамику, скорее всего, в нём смешано несколько вопросов.

## Не дублируйте один ответ разными типами Chart

`Pie`, `Bar`, `Treemap` и `Table` с одними и теми же продажами по регионам редко нужны одновременно.

Оставьте представление, которое лучше отвечает задаче. Таблица нужна отдельно, если важны точные значения или детализация.

## Цвет и названия должны быть стабильными

Цвет имеет смысл, если кодирует статус, порог, серию, категорию или отклонение. Случайная раскраска ради разнообразия только добавляет шум.

Один и тот же KPI на разных графиках лучше называть одинаково.

## Главное не должно прятаться внизу

Обзорная часть панели должна без долгой прокрутки отвечать хотя бы на три вопроса:

```text
что происходит?
есть ли отклонение?
где оно?
```

Если главный KPI находится после длинной стены вспомогательных графиков, порядок стоит пересмотреть.

## Элементы компоновки Superset

В `Layout elements` доступны:

```text
Tabs
Row
Column
Header
Markdown
Divider
```

Используйте их по смыслу.

### `Row`

Группирует связанные блоки в горизонтальный ряд. Удобно для KPI и графиков одного уровня.

### `Column`

Помогает собрать вертикальную структуру внутри области Dashboard.

### `Header`

Отделяет смысловые разделы, например «Ключевые показатели», «Динамика», «Причины отклонений», «Детализация».

### `Markdown`

Подходит для короткого пояснения, единицы измерения или методической оговорки. Dashboard не стоит превращать в длинную инструкцию.

### `Divider`

Разделяет крупные смысловые блоки. Между каждым графиком он не нужен.

### `Tabs`

Полезны, когда на одной панели есть несколько связанных представлений, которые необязательно видеть одновременно.

Tabs не должны быть способом спрятать перегруженность. Если темы действительно разные, иногда лучше сделать отдельные Dashboard.

## Размер блока должен соответствовать содержимому

`Big Number` обычно не требует много места. Временному графику нужна ширина для оси. Размер `Bar Chart` зависит от числа категорий. Таблице нужна ширина для колонок и место для строк.

Размер выбирается по содержимому, а не ради симметричной сетки.

## Когда панель пора разделять

Если Dashboard разросся до десятков графиков, множества фильтров и нескольких несвязанных задач, это уже хороший повод разделить аналитику.

Например:

```text
Обзор
Детальный анализ
Специализированный контроль
```

## Пример структуры

```text
┌────────────────────────────────────────────┐
│ KPI 1   KPI 2   KPI 3   KPI 4             │
├────────────────────────────────────────────┤
│ Динамика                                   │
├─────────────────────┬──────────────────────┤
│ Сравнение категорий │ Причины / структура  │
├─────────────────────┴──────────────────────┤
│ Детальная таблица                          │
└────────────────────────────────────────────┘
```

Это не шаблон, который нужно копировать в каждый Dashboard. Он лишь показывает естественный переход от обзора к деталям.

## Фильтры должны быть предсказуемыми

Пользователь должен понимать, какие фильтры активны, какие графики они меняют и как вернуть исходное состояние.

Подробнее:

→ [Справочник: как выбрать Native Filter](09a-choose-native-filter.md)

## Перед публикацией

Проверьте:

- понятно ли, для кого сделан Dashboard;
- видны ли главные показатели;
- отвечает ли каждый график на отдельный вопрос;
- нет ли бессмысленного дублирования;
- понятны ли названия метрик и графиков;
- несёт ли цвет смысл;
- идёт ли детализация после обзора;
- понятна ли область действия фильтров;
- проверены ли контрольные числа.

Если эти вещи в порядке, дальнейшая полировка уже относится к оформлению, а не к архитектуре панели.
