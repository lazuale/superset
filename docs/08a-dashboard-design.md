# Шпаргалка к уроку 08. Как собрать нормальный Dashboard

Эта шпаргалка не про кнопку `Save` и не про перетаскивание Chart.

Она отвечает на вопрос:

> **как собрать Dashboard так, чтобы человек быстро понял состояние дел и мог провалиться в детали?**

Главное правило:

```text
Dashboard — не склад графиков.
Dashboard — последовательность ответов на вопросы.
```

---

## 1. Сначала сформулируйте задачу Dashboard

Перед добавлением первого Chart ответьте:

```text
Кто будет смотреть Dashboard?
Что он должен понять за 10–20 секунд?
Какое решение он должен принять?
Какие отклонения требуют внимания?
Какая детализация нужна после обнаружения проблемы?
```

Если ответа нет, выбор Chart и layout будет случайным.

---

# 2. Базовая структура рабочего Dashboard

Для большинства управленческих и операционных панелей подходит порядок:

```text
верх
→ ключевые KPI

ниже
→ динамика

ниже
→ сравнение категорий / структура

ниже
→ причины / отклонения

низ
→ детальная таблица
```

Упрощённо:

```text
┌────────────────────────────────────────────┐
│ KPI 1   KPI 2   KPI 3   KPI 4             │
├─────────────────────┬──────────────────────┤
│ Динамика            │ Основное сравнение  │
├─────────────────────┼──────────────────────┤
│ Причины / структура │ Отклонения           │
├─────────────────────┴──────────────────────┤
│ Детальная таблица                         │
└────────────────────────────────────────────┘
```

Это не жёсткий шаблон, а хороший старт.

---

# 3. Верх Dashboard — ответы на «сколько сейчас?»

Для верхнего уровня чаще всего подходят:

```text
Big Number
Big Number Total
```

Примеры:

```text
Выручка
Прибыль
Количество операций
Количество ошибок
Доля ошибок
Выполнение плана
```

Верхняя строка должна показывать самые важные показатели, а не все доступные метрики.

---

## Сколько KPI ставить

Обычно достаточно:

```text
3–6 ключевых KPI
```

Если сверху 12–15 одинаково крупных чисел, пользователь перестаёт понимать, какие из них важнее.

Лучше показать 4 главных KPI и дать детали ниже, чем сделать стену из чисел.

---

# 4. После KPI покажите динамику

KPI отвечает:

> сколько?

Но не отвечает:

> становится лучше или хуже?

Поэтому следующий логичный уровень — временной Chart.

Например:

```text
Time-series Line
Time-series Bar
Mixed Time-series
```

Примеры:

```text
ошибки по дням
выручка по месяцам
факт и план по неделям
остаток незакрытых задач во времени
```

---

# 5. Потом сравните категории

Следующий вопрос:

> где именно находится объём или проблема?

Обычно:

```text
Bar Chart
Treemap
Heatmap
```

Примеры:

```text
ошибки по участкам
выручка по регионам
затраты по подразделениям
тип ошибки × участок
```

Для точного сравнения большого числа категорий `Bar Chart` обычно понятнее `Pie Chart`.

---

# 6. Детализацию ставьте ниже итогов

Таблица нужна, когда пользователь уже понял:

```text
что произошло
и где искать
```

Тогда он может перейти к конкретным строкам.

Хороший порядок:

```text
KPI
↓
аномалия на графике
↓
категория проблемы
↓
Table с конкретными объектами
```

Плохой порядок:

```text
сразу огромная таблица на весь экран
↓
где-то ниже KPI
```

---

# 7. Один Chart — один основной вопрос

Перед каждым Chart сформулируйте его вопрос одной фразой.

Например:

```text
Как меняется количество ошибок по дням?
```

или:

```text
На каком участке больше всего ошибок?
```

Если Chart одновременно пытается показать:

```text
объём
процент
план
факт
среднее
структуру
динамику
```

то его обычно нужно разделить.

---

# 8. Не дублируйте один ответ разными Chart

Плохой Dashboard:

```text
Pie: продажи по регионам
Bar: продажи по регионам
Table: продажи по регионам
Treemap: продажи по регионам
```

Четыре визуализации отвечают на один вопрос.

Это не аналитика, а визуальный шум.

Оставьте форму, которая лучше отвечает задаче, а таблицу — только если нужна точная детализация.

---

# 9. Pie Chart используйте ограниченно

Pie/Donut хорошо работает, если:

```text
частей мало
части образуют целое
важно увидеть долю
```

Например:

```text
ОК / Ошибка / Нет данных
```

Если категорий 15, используйте `Bar Chart` или `Treemap`.

Практическое правило:

```text
Pie / Donut → примерно до 5–7 категорий
```

---

# 10. Цвет должен нести смысл

Не используйте цвет только ради разнообразия.

Хорошие причины для цвета:

```text
разные серии
статус
порог
отклонение
категория
```

Плохая причина:

> «каждый столбец пусть будет своего цвета, так красивее».

Если один и тот же статус встречается в нескольких Chart, желательно сохранять одинаковую визуальную логику.

---

# 11. Не заставляйте пользователя запоминать разные названия одного KPI

Если один показатель называется:

```text
Прибыль
```

на Big Number, то на другом Chart лучше не превращать его без причины в:

```text
Profit total
Маржа итог
Финансовый результат
```

Одинаковая Metric должна иметь одинаковое понятное имя.

Сохранённые Metrics в Dataset помогают поддерживать единое определение.

---

# 12. Фильтры должны быть предсказуемыми

Пользователь должен понимать:

```text
какие фильтры активны
какие Chart они меняют
как вернуть исходное состояние
```

Не делайте десятки фильтров «на всякий случай».

На основной панели обычно нужны только фильтры, которыми реально будут пользоваться.

Подробнее:

→ [Шпаргалка: как выбрать Native Filter](09a-choose-native-filter.md)

---

# 13. Самые важные вещи — без прокрутки

Если пользователь открывает Dashboard для контроля состояния, первый экран должен отвечать хотя бы на вопросы:

```text
что сейчас происходит?
есть ли проблема?
где она?
```

Не прячьте главный KPI в самом низу после десяти вспомогательных графиков.

---

# 14. Размер Chart должен соответствовать его содержимому

### Big Number

Не требует половины экрана.

### Line Chart

Нужна достаточная ширина, чтобы различать временную ось.

### Bar Chart

Если категорий много, нужен больший размер или горизонтальная компоновка, если она доступна и уместна.

### Table

Обычно требует ширины и находится ниже обзорных Chart.

Размер блока — часть читаемости Dashboard.

---

# 15. Не перегружайте Dashboard

Проблема начинается, когда Dashboard превращается в:

```text
20–30 Chart
+ десятки фильтров
+ несколько вкладок без ясной структуры
```

Технически Superset может это отобразить, но пользователю будет трудно понять панель, а каждый Chart создаёт аналитическую и вычислительную нагрузку.

Если вопросов слишком много, лучше разделить их на несколько связанных Dashboard по задачам.

---

# 16. Разделяйте обзор и расследование

Хорошая архитектура может быть такой:

```text
Dashboard 1 — Обзор
→ KPI
→ основные тренды
→ главные отклонения

Dashboard 2 — Детальный анализ
→ больше измерений
→ причины
→ таблицы

Dashboard 3 — Специализированный контроль
→ отдельный процесс / направление
```

Не обязательно помещать весь аналитический мир на одну страницу.

---

# 17. Dashboard не исправляет плохой Chart

Если внутри Chart неправильная Metric или Filter, изменение layout не поможет.

Разделение ответственности:

```text
Dataset / Metric / Chart
→ что и как считается

Dashboard
→ как готовые Chart собраны вместе
```

Если число неверное:

→ [Почему цифры в Superset не сходятся](07b-troubleshoot-wrong-numbers.md)

---

# 18. Начинайте с чернового макета

До настройки цветов и мелких деталей полезно разложить Dashboard в виде блоков:

```text
[KPI] [KPI] [KPI]

[динамика                    ]

[категории       ] [структура]

[детальная таблица           ]
```

После этого проверить:

```text
есть ли логика чтения сверху вниз?
нет ли дублирования?
каждый блок отвечает на свой вопрос?
```

И только потом заниматься оформлением.

---

# 19. Пример рабочего операционного Dashboard

Задача:

> контролировать качество обработки операций.

### Верх

```text
Операций всего
Ошибок
Доля ошибок
Не обработано
```

### Динамика

```text
Line Chart
→ ошибки по дням
```

### Где проблема

```text
Bar Chart
→ ошибки по участкам
```

### Что за проблема

```text
Heatmap
→ участок × тип ошибки
```

### Детали

```text
Table
→ конкретные проблемные записи
```

Пользователь проходит путь:

```text
есть проблема?
↓
когда появилась?
↓
где?
↓
какого типа?
↓
какие конкретно записи?
```

Это и есть связный Dashboard.

---

# 20. Чек-лист перед публикацией

```text
[ ] Понятно, для кого сделан Dashboard.
[ ] Главный вопрос панели понятен.
[ ] Ключевые KPI находятся сверху.
[ ] Каждый Chart отвечает на отдельный вопрос.
[ ] Нет бессмысленного дублирования.
[ ] Названия Metrics и Chart понятны.
[ ] Временная динамика имеет корректный Time grain.
[ ] Фильтры имеют понятный Scoping.
[ ] Главная информация видна без долгой прокрутки.
[ ] Детальная таблица находится после обзорных блоков.
[ ] Контрольные цифры проверены.
[ ] Dashboard сохранён.
[ ] Статус публикации выбран осознанно.
```

---

# 21. Главное правило

```text
Хороший Dashboard ведёт пользователя
от состояния
к отклонению
к причине
к деталям.
```

Не оценивайте Dashboard по количеству Chart.

Оценивайте его по тому, насколько быстро пользователь получает правильный ответ.
