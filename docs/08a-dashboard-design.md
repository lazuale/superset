# Справочник к уроку 08. Как спроектировать нормальный Dashboard

Этот материал дополняет урок 08 методикой. Урок показывает, **как собрать Dashboard в интерфейсе**, а здесь разбирается, **как решить, что на нём должно быть и в каком порядке**.

Главное правило:

```text
Dashboard — не склад Chart.
Dashboard — последовательность ответов на вопросы.
```

## Быстрая схема

```text
верх
→ ключевые KPI

ниже
→ динамика

ниже
→ сравнение категорий / структура

ниже
→ причины и отклонения

низ
→ детальная таблица
```

## 1. Сначала определите задачу панели

Перед первым Chart ответьте:

```text
Кто смотрит Dashboard?
Что он должен понять за 10–20 секунд?
Какое решение он принимает?
Какие отклонения требуют внимания?
Какие детали нужны после обнаружения проблемы?
```

Без этого layout будет случайным.

## 2. Верх — только главные KPI

Чаще всего:

```text
3–6 ключевых KPI
```

Например:

```text
операций всего
ошибок
доля ошибок
не обработано
```

Не превращайте верх в стену из 12–15 одинаково крупных чисел.

## 3. После KPI покажите динамику

KPI отвечает:

```text
сколько сейчас?
```

Временной Chart отвечает:

```text
становится лучше или хуже?
```

Обычно подходят:

```text
Line
Time-series Bar
Mixed Time-series
```

## 4. Затем покажите, где находится проблема

Типовые варианты:

```text
Bar Chart
→ сравнение категорий

Heatmap
→ сочетание двух измерений

Treemap
→ вклад многих категорий
```

Пример:

```text
ошибки по участкам
тип ошибки × участок
```

## 5. Детализацию ставьте после обзора

Нормальный путь пользователя:

```text
есть проблема?
↓
когда появилась?
↓
где?
↓
какого типа?
↓
какие конкретно записи?
```

Поэтому большая `Table` чаще полезнее внизу, а не первой на экране.

## 6. Один Chart — один основной вопрос

Перед каждым Chart сформулируйте одну фразу:

```text
Как меняется количество ошибок по дням?
```

или:

```text
На каком участке больше всего ошибок?
```

Если один Chart одновременно пытается показать объём, процент, план, факт, среднее, структуру и динамику, его обычно нужно разделить.

## 7. Не дублируйте один ответ четырьмя визуализациями

Плохо:

```text
Pie: продажи по регионам
Bar: продажи по регионам
Treemap: продажи по регионам
Table: продажи по регионам
```

Оставьте основной Chart, который лучше отвечает вопросу. Таблицу добавляйте, если действительно нужны точные значения или детализация.

## 8. Цвет и названия должны быть стабильными

Цвет полезен, если кодирует:

```text
статус
порог
серию
категорию
отклонение
```

Не раскрашивайте каждый столбец случайным цветом ради разнообразия.

Один KPI на разных Chart должен иметь одинаковое понятное имя.

## 9. Важное — без длинной прокрутки

Первый экран обзорного Dashboard должен по возможности отвечать:

```text
что происходит?
есть ли отклонение?
где оно?
```

Не прячьте главный KPI внизу после десятка вспомогательных Chart.

## 10. Layout elements Superset: зачем они нужны

Урок 08 показывает элементы:

```text
Tabs
Row
Column
Header
Markdown
Divider
```

Используйте их по смыслу.

### `Row`

Группирует блоки в горизонтальный ряд. Удобно для нескольких KPI или связанных Chart одного уровня.

### `Column`

Помогает организовать вертикальную структуру внутри области Dashboard.

### `Header`

Даёт короткий заголовок смыслового раздела:

```text
Ключевые показатели
Динамика
Причины отклонений
Детализация
```

### `Markdown`

Используйте для короткого пояснения, методики, единицы измерения или предупреждения. Не превращайте Dashboard в длинную инструкцию.

### `Divider`

Визуально разделяет крупные смысловые блоки. Не нужен между каждым Chart.

### `Tabs`

Подходит, когда на одной панели есть несколько связанных представлений, которые не нужно видеть одновременно.

Не используйте Tabs просто для того, чтобы спрятать перегруженность. Если темы разные, иногда лучше два Dashboard.

## 11. Размер блока должен соответствовать содержимому

```text
Big Number
→ компактный блок

Line
→ нужна ширина для временной оси

Bar
→ размер зависит от числа категорий

Table
→ обычно нужна ширина и место для строк
```

## 12. Когда разделять Dashboard

Если получилось:

```text
20–30 Chart
+ много фильтров
+ несколько несвязанных задач
```

это сигнал разделить аналитику.

Например:

```text
Dashboard 1 — Обзор
Dashboard 2 — Детальный анализ
Dashboard 3 — Специализированный контроль
```

## 13. Пример структуры

```text
┌────────────────────────────────────────────┐
│ KPI 1   KPI 2   KPI 3   KPI 4             │
├────────────────────────────────────────────┤
│ Динамика                                   │
├─────────────────────┬──────────────────────┤
│ Сравнение категорий │ Причины / структура  │
├─────────────────────┴──────────────────────┤
│ Детальная таблица                          │
└────────────────────────────────────────────┘
```

## 14. Фильтры должны быть предсказуемыми

Пользователь должен понимать:

```text
какие фильтры активны
какие Chart они меняют
как вернуть исходное состояние
```

Подробно:

→ [Справочник: как выбрать Native Filter](09a-choose-native-filter.md)

## Чек-лист перед публикацией

```text
[ ] Понятно, для кого сделан Dashboard.
[ ] Главный вопрос панели понятен.
[ ] Ключевые KPI сверху.
[ ] Каждый Chart отвечает на отдельный вопрос.
[ ] Нет бессмысленного дублирования.
[ ] Названия Metrics и Chart понятны.
[ ] Цвет несёт смысл.
[ ] Главная информация не спрятана глубоко.
[ ] Детализация идёт после обзора.
[ ] Tabs/Rows/Columns используются осознанно.
[ ] Фильтры имеют понятный Scoping.
[ ] Контрольные числа проверены.
```

## Главное

```text
состояние
→ отклонение
→ причина
→ детали
```

Такой порядок обычно полезнее набора несвязанных графиков.
