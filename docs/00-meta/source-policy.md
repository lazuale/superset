# Политика источников

## Базовое правило

Любое существенное техническое утверждение должно иметь проверяемое основание для baseline из [`release-baseline.md`](release-baseline.md).

Чтение документации, проверка реализации и воспроизведение на стенде — разные виды подтверждения.

## Иерархия доказательств

### 1. Release tree 6.1.0

Основной immutable anchor:

```text
repository: apache/superset
tag:        6.1.0
commit:     c83fb2bb1dcfac41ac51bcebd82471f4a7180d18
```

Используется для документации, исходного кода, конфигурации, migrations и deployment-файлов, реально находящихся в release tree.

### 2. Official versioned docs snapshot

Для generated/versioned documentation, отсутствующей в release tree, используется официальный snapshot:

```text
commit: 6fa0b4875228480ecf9ecd687c5c74c2e30c726b
```

Страница обязательно указывается вместе с конкретным path и этим ref.

### 3. Реализация release tag

Если документация неполна, неоднозначна или расходится с другой официальной страницей, проверяются source/config/migrations release tag `6.1.0`.

### 4. Release notes

Release notes и changelog используются для истории изменения поведения и upgrade-контекста.

### 5. Стенд 6.1.0

Если утверждение относится к фактическому runtime-поведению и его можно воспроизвести, выполняется lab с известными входными условиями и ожидаемым результатом.

## Что не является нормативным источником

- `Next` и `master` без проверки относительно baseline;
- более новая stable-документация;
- внешние блоги и vendor guides;
- Stack Overflow и форумы;
- видеокурсы;
- ответы генеративных систем.

Официальная документация PostgreSQL, SQLAlchemy, Redis, Celery и других зависимостей используется только для поведения соответствующей зависимости и не подменяет источник по Superset.

## Формат фиксации источника

Минимум:

```text
upstream: apache/superset
version:  6.1.0
ref:      <release commit или versioned-docs commit>
path:     <точный путь>
section:  <раздел / config key / class / function — при необходимости>
```

Общая ссылка на главную документации недостаточна.

## Статусы основания

**Документировано** — поведение прямо описано в официальном материале, закреплённом за baseline.

**Проверено по реализации** — поведение подтверждено source/config/migration/deployment-файлом release tag.

**Воспроизведено** — поведение фактически проверено на стенде 6.1.0 с зафиксированными условиями и результатом.

**Учебный вывод** — наше объяснение, архитектурное решение или рекомендация, построенные на подтверждённых фактах. Такой вывод не выдаётся за прямое требование Apache Superset.

## Работа с расхождениями

Если официальные материалы расходятся:

```text
documentation baseline
        ↓
source / config / migrations release tag
        ↓
release notes, если релевантны
        ↓
стенд 6.1.0, если применимо
```

Само расхождение и основание выбранного объяснения фиксируются явно. Если установить результат однозначно нельзя, ограничение проверки указывается прямо.

## Практические материалы

Для procedure или lab, требующих выполнения, фиксируются:

- версия Superset;
- существенные версии внешних компонентов;
- исходное состояние;
- команды или действия;
- ожидаемый результат;
- способ проверки;
- reset/rebuild для сохраняемого состояния.

Lab со статусом `Проверка на стенде: не выполнена` может существовать в draft PR, но не считается готовым к merge.

## Авторство и лицензирование

Основной текст wiki формулируется самостоятельно. Официальная документация не копируется целыми разделами.

Если требуется существенный upstream-фрагмент, отдельно проверяются его лицензия и необходимые notices. Лицензия этой wiki не должна автоматически приписываться чужому Apache-licensed материалу.
