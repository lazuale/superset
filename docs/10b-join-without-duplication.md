# Шпаргалка после урока 10. JOIN без размножения данных

Эта шпаргалка нужна после знакомства с SQL Lab.

Главный риск JOIN в аналитике:

> запрос выполнился без ошибки, но одна исходная строка размножилась и KPI стали неверными.

Короткая схема:

```text
знаю зерно слева
        ↓
знаю зерно справа
        ↓
знаю ключ JOIN
        ↓
понимаю кардинальность
        ↓
сравниваю COUNT и контрольные SUM до/после
```

## 1. Базовая форма JOIN

```sql
SELECT
    ...
FROM table_a AS a
LEFT JOIN table_b AS b
    ON b.key = a.key;
```

Упрощённо:

```text
INNER JOIN
→ оставить строки, где соответствие найдено с обеих сторон

LEFT JOIN
→ сохранить все строки слева; если совпадения справа нет, поля справа будут NULL
```

`LEFT JOIN` не защищает от дублирования: если справа найдено три совпадения, одна строка слева станет тремя строками результата.

## 2. Кардинальность

Перед JOIN определите отношение ключей.

```text
1:1
→ одной строке слева соответствует максимум одна строка справа

N:1
→ многим строкам факта соответствует одна строка справочника

1:N
→ одной строке слева соответствует несколько строк справа

N:M
→ несколько строк с обеих сторон могут совпадать друг с другом
```

Для обычного присоединения справочника к фактам чаще всего ожидается `N:1`.

## 3. Как возникает завышенная сумма

Факт:

| sale_id | region | revenue |
|---:|---|---:|
| 101 | Север | 1000 |

Справочник ошибочно содержит три строки для `Север`:

| region | group |
|---|---|
| Север | A |
| Север | B |
| Север | C |

После JOIN:

| sale_id | revenue | group |
|---:|---:|---|
| 101 | 1000 | A |
| 101 | 1000 | B |
| 101 | 1000 | C |

Теперь:

```text
SUM(revenue) = 3000
```

Хотя реальная продажа одна и её выручка — `1000`.

Superset здесь не обязан показывать ошибку: SQL технически корректен.

## 4. Проверяйте число строк до и после

Минимальный контроль:

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT sale_id) AS sales
FROM ...;
```

Например:

```text
до JOIN:
rows  = 12
sales = 12

после JOIN:
rows  = 18
sales = 12
```

Это сильный сигнал, что часть продаж размножилась.

## 5. Проверяйте контрольные суммы

Если JOIN только добавляет атрибут справочника, исходные аддитивные показатели не должны неожиданно изменяться.

Для `training.sales` контроль:

```text
rows    = 12
sales   = 12
revenue = 4005.00
cost    = 2475.00
```

После JOIN снова проверьте:

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT sale_id) AS sales,
    SUM(revenue) AS revenue,
    SUM(cost) AS cost
FROM ...;
```

Если `revenue` вырос, а задача JOIN не должна была менять продажи, дальше строить Chart нельзя.

## 6. Проверьте уникальность справочника

Если ожидается одна строка справочника на ключ:

```sql
SELECT
    region,
    COUNT(*) AS cnt
FROM region_directory
GROUP BY region
HAVING COUNT(*) > 1;
```

Если запрос возвращает строки, ключ `region` не уникален.

## 7. Когда вторая таблица законно имеет много строк

Например:

```text
1 продажа
→ несколько платежей
```

Если итоговый Dataset должен остаться на уровне продажи, сначала приведите платежи к тому же зерну:

```sql
WITH payments_by_sale AS (
    SELECT
        sale_id,
        SUM(amount) AS payment_amount
    FROM payments
    GROUP BY sale_id
)
SELECT
    s.sale_id,
    s.revenue,
    p.payment_amount
FROM sales AS s
LEFT JOIN payments_by_sale AS p
    ON p.sale_id = s.sale_id;
```

Сначала:

```text
много платежей
→ 1 строка на sale_id
```

и только потом JOIN.

## 8. Не лечите JOIN через `DISTINCT`

Такой патч:

```sql
SELECT DISTINCT ...
```

не исправляет неправильную кардинальность.

Он может:

- случайно скрыть часть дублей;
- не убрать строки, отличающиеся одним полем;
- удалить реальные одинаковые записи;
- оставить причину ошибки в модели.

Исправляйте ключ JOIN, источник или зерно второй стороны.

## 9. `COUNT(DISTINCT ...)` тоже не лечит всё

После размножения:

```sql
COUNT(DISTINCT sale_id)
```

может вернуть правильное число продаж.

Но:

```sql
SUM(revenue)
AVG(revenue)
```

могут остаться неправильными.

Поэтому `COUNT DISTINCT` не является ремонтом JOIN.

```text
[ ] COUNT(DISTINCT business_id) сравнен.
[ ] Контрольные SUM до и после сравены.

```

## Главное

```text
JOIN без SQL-ошибки
≠
аналитически правильный JOIN
```

Сначала проверяйте зерно и контрольные числа, только потом сохраняйте результат как `Virtual Dataset` и стройте Chart.
