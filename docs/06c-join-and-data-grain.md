# Шпаргалка к урокам 06 и 10. JOIN и зерно данных

Эта шпаргалка нужна, чтобы не получить красивый Dashboard с неправильными цифрами.

Главный вопрос перед любыми расчётами и JOIN:

> **что означает одна строка Dataset?**

Это и есть зерно данных (`grain`).

Самая короткая схема:

```text
1 строка = что?
        ↓
какой объект или событие она представляет?
        ↓
может ли JOIN создать несколько строк вместо одной?
        ↓
если да — суммы, COUNT и AVG могут измениться
```

---

## 1. Что такое зерно данных

Зерно — смысл одной строки набора данных.

Для учебной таблицы:

```text
training.sales
```

зерно такое:

```text
1 строка = 1 продажа
```

Это означает, что поля `revenue`, `cost`, `quantity` относятся к конкретной продаже.

Пока одна продажа представлена одной строкой, выражение:

```sql
SUM(revenue)
```

суммирует выручку продаж один раз.

---

## 2. Почему зерно нужно знать до Metric

Допустим, есть 100 строк и каждая строка — одна продажа.

Тогда:

```text
COUNT(*) = 100 продаж
```

Но если одна продажа может занимать несколько строк, то:

```text
COUNT(*)
```

уже считает строки, а не продажи.

Для количества продаж тогда может понадобиться:

```sql
COUNT(DISTINCT sale_id)
```

Поэтому сначала определяется зерно, и только потом выбирается агрегирование.

---

# 3. Что делает JOIN

`JOIN` соединяет строки нескольких таблиц по условию.

Пример:

```text
sales
+
region_directory
```

SQL:

```sql
SELECT
    s.sale_id,
    s.region,
    s.revenue,
    r.region_group
FROM training.sales AS s
LEFT JOIN region_directory AS r
    ON r.region = s.region;
```

Если каждой строке `sales` соответствует ровно одна строка справочника, зерно может сохраниться:

```text
до JOIN:
1 строка = 1 продажа

после JOIN:
1 строка = 1 продажа
```

Но это нужно проверять, а не предполагать.

---

# 4. Самая опасная ситуация: JOIN размножил строки

Допустим, в `sales` есть одна продажа:

| sale_id | region | revenue |
|---:|---|---:|
| 101 | Север | 1000 |

А в справочнике по ошибке три строки для `Север`:

| region | group |
|---|---|
| Север | A |
| Север | B |
| Север | C |

После JOIN получится:

| sale_id | region | revenue | group |
|---:|---|---:|---|
| 101 | Север | 1000 | A |
| 101 | Север | 1000 | B |
| 101 | Север | 1000 | C |

Исходная продажа была одна, но теперь она представлена тремя строками.

Тогда:

```sql
SUM(revenue)
```

даст:

```text
3000
```

вместо:

```text
1000
```

Superset не обязан считать это ошибкой SQL. Запрос технически корректен — неверна аналитическая модель.

---

# 5. Кардинальность JOIN

Перед JOIN полезно понимать отношения таблиц.

## Один к одному — `1:1`

```text
одна продажа
↔
одна строка справочника
```

Обычно зерно сохраняется.

---

## Многие к одному — `N:1`

```text
много продаж
→
один регион
```

Это нормальная ситуация для присоединения справочника к фактам.

Например:

```text
много sales
→ один region_directory.region
```

Если справочник действительно уникален по ключу, число строк продаж не увеличивается.

---

## Один ко многим — `1:N`

```text
одна продажа
→
несколько строк второй таблицы
```

Здесь исходная строка размножается.

Это уже требует осознанного решения.

---

## Многие ко многим — `N:M`

Самый рискованный случай.

```text
несколько строк слева
↔
несколько строк справа
```

Количество строк результата может резко увеличиться.

Такой JOIN нельзя делать механически, если после него считаются суммы или средние.

---

# 6. Проверка до и после JOIN

Минимальный контроль:

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT sale_id) AS sales
FROM ...;
```

Сравните до и после JOIN.

Например:

```text
до:
rows  = 12
sales = 12

после:
rows  = 18
sales = 12
```

Это означает:

```text
часть продаж размножилась
```

Если рост строк не был ожидаемым — дальше считать KPI нельзя.

---

# 7. Проверяйте суммы до и после JOIN

Для важных аддитивных показателей сравните контрольные суммы.

Например:

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT sale_id) AS sales,
    SUM(revenue) AS revenue,
    SUM(cost) AS cost
FROM ...;
```

Для `training.sales` ожидается:

```text
rows    = 12
sales   = 12
revenue = 4005.00
cost    = 2475.00
```

Если JOIN предназначен только для добавления атрибута справочника, а `revenue` внезапно стал больше — зерно нарушено.

---

# 8. Как проверить уникальность справочника

Перед JOIN по ключу:

```text
region
```

проверьте:

```sql
SELECT
    region,
    COUNT(*) AS cnt
FROM region_directory
GROUP BY region
HAVING COUNT(*) > 1;
```

Если запрос возвращает строки, ключ не уникален.

То есть предположение:

```text
один region → одна строка справочника
```

не выполняется.

---

# 9. Не лечите размножение строк через DISTINCT вслепую

Типичная попытка:

```sql
SELECT DISTINCT ...
```

Иногда она случайно уменьшает число строк, но не исправляет модель.

Почему:

- строки могут отличаться хотя бы одним полем;
- можно скрыть настоящие дубли;
- можно удалить две реальные одинаковые по выбранным полям записи;
- причина неправильной кардинальности останется.

Сначала исправляется логика JOIN или источник данных.

---

# 10. Не лечите неправильный JOIN через COUNT DISTINCT повсюду

Если JOIN размножил строки, выражение:

```sql
COUNT(DISTINCT sale_id)
```

может вернуть правильное количество продаж.

Но:

```sql
SUM(revenue)
```

по-прежнему останется неправильным.

Поэтому `COUNT DISTINCT` — не универсальный способ исправить зерно.

---

# 11. Когда нужно сначала агрегировать таблицу

Иногда вторая таблица законно содержит много строк на один объект.

Например:

```text
sale_id
→ несколько платежей
```

Если Dashboard нужен на уровне продажи, можно сначала привести платежи к зерну продажи:

```sql
WITH payments_by_sale AS (
    SELECT
        sale_id,
        SUM(amount) AS payment_amount
    FROM payments
    GROUP BY sale_id
)
SELECT ...
FROM sales s
LEFT JOIN payments_by_sale p
    ON p.sale_id = s.sale_id;
```

То есть сначала:

```text
много платежей
→ 1 строка на sale_id
```

и только затем JOIN к таблице продаж.

---

# 12. Одно зерно на один аналитический Dataset

Хорошая практика — уметь закончить фразу:

```text
1 строка этого Dataset = ...
```

Например:

```text
1 строка = продажа
1 строка = автомобиль за сутки
1 строка = сотрудник за смену
1 строка = транзакция
1 строка = заказ
```

Если ответ звучит как:

> «ну там иногда продажа, иногда строка платежа, иногда ещё что-то»

Dataset уже трудно безопасно агрегировать.

---

# 13. Зерно и Dimensions

`Dimension` не меняет исходный смысл строки Dataset.

Если:

```text
1 строка = продажа
```

то:

```text
Dimension = region
```

означает:

```text
собрать продажи в группы по region
```

Metric затем считается внутри каждой группы.

Поэтому ошибка зерна существует ещё до выбора Chart.

---

# 14. Зерно и Virtual Dataset

Virtual Dataset может изменить зерно.

Например:

```sql
SELECT
    region,
    SUM(revenue) AS revenue
FROM training.sales
GROUP BY region
```

Теперь результат имеет зерно:

```text
1 строка = 1 регион
```

а не:

```text
1 строка = 1 продажа
```

Если затем в Chart снова бездумно агрегировать уже агрегированное значение, легко получить неправильную модель расчёта.

На базовом маршруте курса Virtual Dataset сохраняет исходное зерно продаж именно для того, чтобы агрегирование выполнялось в Explore.

---

# 15. Зерно и AVG

Среднее особенно чувствительно к размножению строк.

Если одна запись появилась три раза после JOIN, она получает тройной вес в:

```sql
AVG(value)
```

Даже когда итог выглядит правдоподобно.

Поэтому для средних контроль зерна так же важен, как для SUM.

---

# 16. Красные флаги

Остановитесь и проверьте SQL, если после JOIN:

- количество строк неожиданно выросло;
- `COUNT(DISTINCT id)` не вырос, а `COUNT(*)` вырос;
- суммы стали кратно больше;
- появились повторяющиеся идентификаторы;
- один объект отображается несколько раз;
- среднее заметно изменилось без понятной причины;
- один и тот же KPI отличается между двумя Dataset.

---

# 17. Минимальный чек перед использованием JOIN в Superset

```text
[ ] Я знаю зерно левой таблицы.
[ ] Я знаю зерно правой таблицы.
[ ] Я знаю ключ JOIN.
[ ] Я проверил уникальность ключа там, где ожидаю N:1.
[ ] Я сравнил COUNT(*) до и после JOIN.
[ ] Я сравнил COUNT(DISTINCT business_id).
[ ] Я сравнил контрольные SUM.
[ ] Рост строк, если он есть, объясним задачей.
[ ] Я понимаю зерно итогового Dataset.
```

Если хотя бы на один пункт ответа нет, не переходите сразу к Dashboard.

---

# 18. Алгоритм для новичка

```text
Что означает одна строка слева?
          ↓
Что означает одна строка справа?
          ↓
По какому ключу соединяем?
          ↓
Сколько строк справа может совпасть с одной строкой слева?
          ↓
1 → обычно безопасный N:1
несколько → возможное размножение
          ↓
проверить COUNT и SUM
          ↓
только потом строить Metric и Chart
```

---

# 19. Главное правило

```text
JOIN, который выполняется без ошибки,
не обязательно аналитически правильный.
```

И второе:

```text
Перед SUM, COUNT и AVG
всегда нужно понимать,
что означает одна строка Dataset.
```
