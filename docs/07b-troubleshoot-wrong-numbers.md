# Справочник к урокам 05–07. Почему цифры в Superset не сходятся

Эта шпаргалка нужна не когда Superset показывает ошибку, а когда он показывает **правдоподобный, но неправильный результат**.

Это опаснее обычной ошибки: запрос выполнился, Chart выглядит нормально, но смысл расчёта уже потерян.

Главное правило:

> сначала проверяем данные и расчёт, и только потом визуализацию.

---

## Аварийный алгоритм

Если число не сходится, идите сверху вниз:

```text
1. Dataset
   ↓
2. Time Range / временной Filter
   ↓
3. обычные Filters
   ↓
4. Dimensions
   ↓
5. Metric
   ↓
6. Aggregation
   ↓
7. NULL
   ↓
8. зерно Dataset
   ↓
9. JOIN / дублирование строк
   ↓
10. контрольный SQL
```

Не меняйте всё сразу. Иначе вы не поймёте, какая настройка была неправильной.

---

# 1. Проверьте Dataset

Первый вопрос:

> Я вообще считаю по тому источнику данных?

В Explore проверьте текущий Dataset.

Похожие Dataset могут содержать:

- разные таблицы;
- разные SQL-запросы;
- разные фильтры внутри Virtual Dataset;
- разные наборы колонок;
- разные версии одной витрины.

Если источник неправильный, дальнейшая настройка Chart уже не имеет значения.

---

# 2. Проверьте период

Очень частая причина неожиданного результата — старый временной фильтр.

Проверьте:

```text
Time Range
или temporal Filter
```

В учебном курсе для всех данных используется:

```text
sale_date (No filter)
```

Для февраля 2026:

```text
Start (inclusive): 2026-02-01
End (exclusive):   2026-03-01
```

Это означает:

```text
2026-02-01 <= sale_date < 2026-03-01
```

Если Chart пустой или показывает только часть ожидаемых данных, период проверяем одним из первых.

---

# 3. Проверьте обычные Filters

Фильтр, оставшийся после прошлого эксперимента, легко забыть.

Например:

```text
region IN Север
```

при вопросе:

> Покажи общую выручку всех регионов.

Metric может быть совершенно правильной, но исходный набор строк уже урезан.

Проверьте каждый активный Filter и проговорите его словами.

---

# 4. Проверьте Dimensions

Dimension отвечает за группировку.

Если ожидались:

```text
Север
Юг
```

а получилось одно число:

```text
4005.00
```

вероятная причина:

```text
Dimensions = пусто
```

Если, наоборот, вместо двух строк получилось двадцать, возможно, добавлен лишний Dimension.

Каждый дополнительный Dimension делает результат детальнее.

---

# 5. Проверьте Metric

Сначала проговорите Metric обычным языком.

```text
SUM(revenue)
→ сумма revenue

COUNT(*)
→ количество строк

COUNT_DISTINCT(manager)
→ количество разных manager
```

Затем сравните это с исходным бизнес-вопросом.

Если вопрос:

> Сколько уникальных автомобилей?

а Metric:

```text
COUNT(*)
```

Superset считает правильно — ошибочна сама постановка расчёта.

---

# 6. Проверьте агрегирование

Одна колонка с разными агрегированиями отвечает на разные вопросы.

Например:

```text
SUM(quantity)
COUNT(quantity)
AVG(quantity)
MAX(quantity)
```

Это четыре разных показателя.

Особенно внимательно проверяйте:

```text
COUNT(*)
COUNT(column)
COUNT_DISTINCT(column)
```

Подробнее:

→ [Как выбрать агрегирование](06a-aggregations.md)

---

# 7. Проверьте NULL

`COUNT(column)` не считает `NULL`.

В учебных данных:

```text
COUNT(*)       = 12
COUNT(manager) = 11
```

Это не ошибка.

Одна строка содержит пустой `manager`.

Если разница между количеством строк и количеством значений неожиданна, проверьте NULL.

---

# 8. Проверьте зерно Dataset

**Зерно** — это ответ на вопрос:

> Что представляет одна строка Dataset?

Например:

```text
одна продажа
одна позиция документа
одна поездка
одна транзакция
один автомобиль за день
один сотрудник за смену
```

Без понимания зерна нельзя безопасно использовать `COUNT(*)` и многие другие Metrics.

Пример:

```text
Документ №100
├── позиция 1
├── позиция 2
└── позиция 3
```

Если одна строка Dataset = одна позиция, то:

```text
COUNT(*) = 3
```

Но документов:

```text
1
```

Для количества документов нужен идентификатор документа и, вероятно:

```text
COUNT_DISTINCT(document_id)
```

---

# 9. Подозревайте JOIN, если число стало кратно больше

Это одна из самых опасных причин завышенных итогов.

Допустим, есть таблица заказов:

```text
order_id | amount
1        | 100
```

и три связанные строки в другой таблице:

```text
order_id | item
1        | A
1        | B
1        | C
```

После обычного JOIN можно получить:

```text
1 | 100 | A
1 | 100 | B
1 | 100 | C
```

Теперь:

```text
SUM(amount) = 300
```

хотя реальная сумма заказа:

```text
100
```

Superset здесь тоже не ошибся: Dataset уже содержит размноженные строки.

Красные флаги JOIN:

- сумма выросла в 2, 3, 10 раз;
- после добавления поля из другой таблицы итог изменился;
- `COUNT(*)` резко увеличился;
- один идентификатор повторяется неожиданно много раз;
- сумма по деталям не равна ожидаемому итогу.

Такие проблемы обычно надо исправлять на уровне SQL, view, materialized view или витрины, а не маскировать настройками Chart.

---

# 10. Проверьте, не суммируете ли уже агрегированное значение

Пример опасной структуры:

```text
month | office | monthly_total
```

Если `monthly_total` уже является месячным итогом, а Dataset содержит несколько строк с повторяющимся итогом, повторный:

```text
SUM(monthly_total)
```

может завысить результат.

Перед `SUM` всегда задавайте вопрос:

> Это исходное значение события или уже готовый итог?

---

# 11. Проверьте средние

Среднее от средних часто неверно.

Пример:

```text
Группа A:
100 строк
AVG = 10

Группа B:
2 строки
AVG = 100
```

Простое:

```text
(10 + 100) / 2
```

не является средним всех исходных строк.

Если нужно корректное общее среднее, расчёт должен выполняться по исходным наблюдениям или учитывать веса групп.

---

# 12. Проверьте Time grain

`Time Range` и `Time grain` — разные вещи.

```text
Time Range
→ какие даты участвуют

Time grain
→ как участвующие даты объединяются в группы
```

Если ожидались месяцы, а появились дни:

```text
Time grain
```

скорее всего выбран неправильно.

Если данные вообще отсутствуют — сначала смотрите `Time Range`.

---

# 13. Уберите лишнее и соберите минимальный запрос

Если Chart сложный, временно упростите его.

Например, вместо:

```text
3 Dimensions
4 Metrics
5 Filters
сложная визуализация
```

оставьте:

```text
Visualization = Table
Dimension     = одна
Metric        = одна
Filter        = только необходимый период
```

Проверьте базовое число.

Затем возвращайте элементы по одному.

Это намного надёжнее, чем хаотично менять настройки.

---

# 14. Table — лучший режим для проверки цифр

Когда вы отлаживаете расчёт, красивый Chart часто мешает.

Временно переключитесь на:

```text
Table
```

Таблица позволяет увидеть:

- группы;
- названия Metrics;
- точные значения;
- лишние Dimensions;
- неожиданные строки.

Сначала добейтесь правильного результата в Table, потом выбирайте финальную визуализацию.

---

# 15. Сравните итог с простым SQL

Если сомнение осталось, воспроизведите расчёт в SQL Lab или напрямую в БД.

Для учебного примера:

```sql
SELECT
    region,
    SUM(revenue) AS revenue
FROM training.sales
GROUP BY region
ORDER BY region;
```

Ожидается:

```text
Север = 1360.00
Юг    = 2645.00
```

Если SQL и Chart дают разные числа, сравнивайте:

- Dataset;
- Filters;
- период;
- Dimensions;
- Metric;
- SQL Virtual Dataset.

Если SQL уже даёт неправильный итог, проблема находится до визуализации.

---

# 16. Не «лечите» неправильное число форматированием

Настройки вроде:

- округления;
- формата процентов;
- количества знаков;
- сортировки;
- цвета;
- типа Chart

не исправляют ошибочную Metric.

`1 200` вместо правильных `137` останется неправильным числом, даже если красиво оформить его как Big Number.

---

# 17. Типовые симптомы

| Симптом | Сначала проверить |
|---|---|
| Chart пустой | Time Range, Filters, Dataset |
| число меньше ожидаемого | Filters, период, NULL |
| число больше ожидаемого | COUNT вместо DISTINCT, JOIN, зерно |
| число выросло кратно | JOIN / дублирование строк |
| одна строка вместо групп | Dimensions |
| слишком много строк | лишние Dimensions |
| вместо объектов считаются записи | `COUNT(*)` vs `COUNT_DISTINCT` |
| месяц разбился по дням | Time grain |
| среднее кажется странным | уровень агрегации, среднее от средних |
| после смены Chart появилась лишняя серия | лишняя Metric в Explore |
| SQL и Chart не совпадают | Dataset, Filters, Metric, период |

---

# 18. Контрольные числа учебного Dataset

Для всех данных:

```text
rows     = 12
quantity = 31
revenue  = 4005.00
cost     = 2475.00
profit   = 1530.00
```

По регионам:

```text
Север:
revenue = 1360.00
profit  = 520.00

Юг:
revenue = 2645.00
profit  = 1010.00
```

Февраль 2026:

```text
revenue = 1180.00
```

Количество менеджеров:

```text
COUNT(*)                 = 12
COUNT(manager)            = 11
COUNT_DISTINCT(manager)   = 4
```

Эти значения можно использовать как эталон при упражнениях курса.

---

# 19. Полный порядок диагностики

Когда результат вызывает сомнение, используйте один и тот же порядок:

```text
Вопрос к данным сформулирован точно?
        ↓
Правильный Dataset?
        ↓
Правильный период?
        ↓
Нет лишних Filters?
        ↓
Правильные Dimensions?
        ↓
Metric отвечает на вопрос словами?
        ↓
Правильная агрегация?
        ↓
Учтены NULL?
        ↓
Понятно зерно Dataset?
        ↓
JOIN не размножил строки?
        ↓
Контрольный SQL даёт тот же результат?
```

Если все пункты пройдены, только после этого имеет смысл искать проблему в конкретном Chart или его отображении.

---

## Главное, что нужно запомнить

Superset чаще всего **не придумывает неправильное число сам**.

Обычно он корректно считает тот запрос, который ему задали.

Задача аналитика — убедиться, что:

```text
Dataset
+ Filters
+ Dimensions
+ Metric
+ Aggregation
```

действительно соответствуют бизнес-вопросу.
