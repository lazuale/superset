# 12. Итоговая проверка и что изучать дальше

## Зачем нужен этот урок

Предыдущие уроки были учебными: в них действия разбирались по шагам.

Этот урок устроен иначе.

Здесь нет новой функции Superset и нет очередной последовательности кнопок.

Задача — проверить, сложился ли из отдельных навыков один рабочий сценарий:

```text
учебный PostgreSQL
        ↓
Database connection
        ↓
Physical Dataset
        ↓
Explore
        ↓
Calculated Column + Metric
        ↓
Chart
        ↓
Dashboard
        ↓
Native Filters
        ↓
SQL Lab
        ↓
Virtual Dataset
        ↓
Chart на Virtual Dataset
```

Если эту цепочку удаётся пройти на чистом стенде без пошаговых инструкций, базовый курс выполнен.

Если на каком-то этапе приходится возвращаться к уроку и повторять действия по пунктам, это не провал всего курса. Это означает, что именно соответствующий навык ещё не закрепился.

## Что в этом уроке сознательно не появляется

Мы не добавляем новые темы только ради того, чтобы финальный урок выглядел сложнее.

Здесь не будет:

- `JOIN`;
- CTE и `WITH`;
- Jinja;
- сложных временных функций;
- новых типов Chart;
- cross-filtering;
- drill-функций;
- RBAC и RLS;
- Alerts & Reports;
- Redis и Celery;
- API;
- embedding;
- production-развёртывания.

Эти темы будут следующими направлениями обучения после базового курса.

# Правила итоговой работы

Итоговую работу лучше выполнять после полного сброса учебного стенда.

Это удалит созданные во время курса:

- Database connection;
- Dataset;
- Metrics;
- Calculated Columns;
- Chart;
- Dashboard;
- Native Filters;
- Virtual Dataset;
- остальные объекты metadata Superset.

Учебная таблица PostgreSQL после повторного запуска будет создана заново из файлов каталога `training/`.

## Важно

Команда полного сброса действительно удаляет Docker volumes учебного стенда.

Используйте её **только для учебного compose-проекта этого курса**.

Из каталога:

```text
training/
```

выполните:

```bash
docker compose down -v --remove-orphans
docker compose up -d
```

После запуска проверьте состояние контейнеров:

```bash
docker compose ps -a
```

И контрольные данные:

```bash
docker compose exec -T db \
  psql -U training -d training -f /training/check.sql
```

Ожидается:

```text
rows     = 12
quantity = 31
revenue  = 4005.00
cost     = 2475.00
profit   = 1530.00
```

Эта проверка стенда разрешена: она не подсказывает, как выполнять работу в Superset.

# Этап 3. Получите результат через Explore

Используя Dataset `sales`, самостоятельно ответьте на вопрос:

> Какова выручка каждого региона по всем учебным данным?

Ожидается:

| region | revenue |
|---|---:|
| Север | 1360.00 |
| Юг | 2645.00 |

Порядок строк не является критерием.

Общая проверка:

```text
1360.00 + 2645.00 = 4005.00
```

После этого измените период и получите выручку только за февраль 2026 года.

Ожидается:

| region | revenue |
|---|---:|
| Север | 450.00 |
| Юг | 730.00 |

Итого:

```text
1180.00
```

### Приёмка этапа

Вы должны самостоятельно определить:

- какое поле использовать для группировки;
- какую агрегацию применить к `revenue`;
- как задать период;
- когда нужно выполнить запрос заново.

Если не получилось — повторите [урок 05](05-explore-basics.md).

# Этап 4. Создайте Calculated Column

В Dataset `sales` создайте вычисляемый столбец:

```text
profit
```

Он должен вычислять прибыль **одной строки продажи**.

### Контроль логики

Для первой строки:

```text
revenue = 200.00
cost    = 120.00
profit  = 80.00
```

Для строки `sale_id = 12`:

```text
revenue = 725.00
cost    = 440.00
profit  = 285.00
```

После сохранения проверьте его через Explore.

Агрегированная сумма `profit` по всем данным должна быть:

```text
1530.00
```

По регионам:

```text
Север = 520.00
Юг    = 1010.00
```

### Приёмка этапа

Вы должны уметь объяснить:

```text
profit
→ расчёт строки
→ Calculated Column
```

Если в выражении Calculated Column вы пытаетесь сначала агрегировать все строки, вернитесь к [уроку 06](06-metrics-and-calculations.md).

---

# Этап 5. Создайте сохранённую Metric

В том же Dataset создайте сохранённую Metric:

```text
Metric Key: total_profit
Label:      Прибыль
```

Она должна вычислять общую прибыль на уровне выбранного набора строк.

### Приёмка этапа

При отсутствии фильтров Metric должна дать:

```text
1530.00
```

При группировке по региону:

```text
Север = 520.00
Юг    = 1010.00
```

Вы должны уметь своими словами объяснить разницу:

```text
revenue - cost
→ одна строка
→ Calculated Column

SUM(revenue) - SUM(cost)
→ набор строк
→ Metric
```

Если эта граница неясна — повторите [урок 06](06-metrics-and-calculations.md), даже если цифры случайно получились правильными.

# Этап 6. Создайте сохранённые Chart

Создайте минимум **два** самостоятельных сохранённых Chart на Dataset `sales`.

Обязательные аналитические задачи:

1. показать выручку и прибыль по регионам;
2. показать изменение выручки по времени с группировкой по месяцам.

Дополнительно можно создать KPI общей прибыли, но для сдачи курса это не обязательно.

### Контрольные значения по регионам

```text
Север:
revenue = 1360.00
profit  = 520.00

Юг:
revenue = 2645.00
profit  = 1010.00
```

### Контрольные значения по месяцам

```text
2026-01 = 1160.00
2026-02 = 1180.00
2026-03 = 1665.00
```

### Приёмка этапа

Нужно уметь:

- выбрать подходящую визуализацию под вопрос;
- использовать сохранённую Metric;
- получить правильный временной результат;
- сохранить Chart;
- найти его в общем списке `Charts`;
- снова открыть и изменить;
- сохранить изменение существующего Chart, а не плодить случайные копии.

Имена Chart выбирайте понятные. Конкретное русское название не является частью проверки.

Если не получилось — повторите [урок 07](07-create-charts.md).

# Этап 7. Соберите Dashboard

Создайте Dashboard и добавьте на него Chart предыдущего этапа.

Разместите их так, чтобы оба результата можно было нормально читать без наложения элементов.

Опубликуйте Dashboard.

После этого:

1. выйдите из него;
2. найдите Dashboard через общий список;
3. откройте снова;
4. войдите в режим редактирования;
5. измените расположение или размер одного Chart;
6. сохраните изменение.

### Приёмка этапа

Вы должны понимать разницу:

```text
Save
→ сохраняет изменения Dashboard

Published
→ определяет статус публикации Dashboard
```

Публикация сама по себе не означает выдачу публичного доступа в Интернет.

Если не получилось — повторите [урок 08](08-build-dashboard.md).

# Этап 8. Добавьте Native Filters

На итоговый Dashboard добавьте два Native Filter:

```text
Период
Регион
```

Оба должны действовать на Chart итогового Dashboard.

### Проверка 1

Без фильтров исходная выручка должна оставаться:

```text
4005.00
```

### Проверка 2

Выберите:

```text
Регион = Север
```

Chart должны перестроиться на данные только этого региона.

Контроль:

```text
revenue = 1360.00
profit  = 520.00
```

### Проверка 3

Одновременно задайте:

```text
Период = февраль 2026
Регион = Север
```

Контроль:

```text
revenue = 450.00
profit  = 175.00
```

Временной Chart при этом должен показывать только февральский результат выбранного региона.

Очистите фильтры и убедитесь, что Dashboard вернулся к исходным данным.

### Приёмка этапа

Вы должны понимать, что `Native Filter` принадлежит Dashboard и имеет собственную область действия (`Scope`).

Если фильтр работает не на все требуемые Chart — сначала проверьте Scope.

Если не получилось — повторите [урок 09](09-native-filters.md).

# Этап 10. Создайте Virtual Dataset

Самостоятельно подготовьте в SQL Lab построчный запрос к `training.sales`, который возвращает исходные поля продаж и дополнительный столбец:

```text
profit
```

При этом:

```text
одна строка результата SQL
=
одна исходная продажа
```

Не агрегируйте данные по регионам внутри этого SQL.

Из результата создайте постоянный Virtual Dataset.

Для удобства назовите его:

```text
sales_virtual
```

### Приёмка Dataset

После сохранения:

- `sales_virtual` находится через `Data → Datasets`;
- исходный физический Dataset `sales` всё ещё существует отдельно;
- Virtual Dataset содержит `profit`;
- Virtual Dataset возвращает 12 учебных продаж;
- в PostgreSQL не требуется создавать новую таблицу `sales_virtual`.

Затем на `sales_virtual` создайте Chart прибыли по регионам.

Контроль:

```text
Север = 520.00
Юг    = 1010.00
```

Сохраните Chart и снова откройте его из списка Charts.

Если не получилось — повторите [урок 11](11-create-virtual-dataset.md).

# Что изучать дальше

После базового курса не нужно пытаться изучить весь Superset сразу.

Следующий трек выбирайте по реальной задаче.

## Трек 1. Аналитик: модель данных и более сильный SQL

Выбирайте этот трек, если основная работа — самостоятельно исследовать данные и строить аналитику.

Следующие темы:

1. структура аналитических таблиц;
2. факты и измерения;
3. зерно данных;
4. корректные агрегирования;
5. `JOIN`;
6. подзапросы;
7. CTE;
8. оконные функции;
9. более сложные Virtual Dataset;
10. проверка SQL до визуализации.

Важный принцип:

```text
плохую модель данных нельзя исправить красивым Dashboard
```

Superset выполняет аналитические запросы поверх источника, поэтому качество модели и SQL напрямую влияет на надёжность аналитики.

## Трек 2. Владелец аналитики: доступы и Row Level Security

Этот трек нужен, когда одним Superset пользуются разные подразделения или группы пользователей.

Изучайте:

1. пользователей;
2. роли;
3. доступ к Dataset;
4. доступ к Database;
5. доступ к Dashboard;
6. `Gamma` и дополнительные роли доступа;
7. `Row Level Security`;
8. проверку результата под разными пользователями.

Не начинайте с ручной выдачи десятков случайных permissions.

Сначала нужно понять модель доступа Superset целиком.

Официальная документация отдельно предупреждает не изменять без необходимости встроенные базовые роли и рекомендует строить ограниченный доступ через дополнительные роли и доступ к данным.

## Трек 3. Администратор: production-развёртывание

Учебный compose-файл **не является production-конфигурацией**.

Для реального сервера отдельно изучаются:

1. архитектура Superset;
2. production metadata database;
3. резервное копирование metadata;
4. собственный `SUPERSET_SECRET_KEY`;
5. HTTPS и reverse proxy;
6. отдельные ограниченные database users;
7. аутентификация;
8. логирование;
9. обновления Superset;
10. staging перед обновлением production.

Официальное руководство по безопасности прямо указывает, что стандартная конфигурация ориентирована на удобство разработки, а не на production security.

Учебные значения:

```text
admin / admin
training / training
training-only SUPERSET_SECRET_KEY
```

никогда не переносятся в реальную среду.

## Трек 4. Производительность: кэш и фоновые задачи

Когда появляется реальная нагрузка, изучаются:

- caching;
- Redis или другой подходящий backend;
- chart data cache;
- async queries;
- worker;
- scheduler/beat;
- Celery;
- нагрузка на аналитическую БД;
- тяжёлые Virtual Dataset;
- материализация расчётов в источнике данных.

Не добавляйте Redis и Celery в систему просто потому, что они существуют.

Они нужны для конкретных функций и архитектурных задач.

## Трек 5. Alerts & Reports

Если Dashboard должен сам отправляться пользователям или нужно уведомление по условию, изучайте `Alerts & Reports`.

Здесь уже понадобятся дополнительные компоненты и настройки, в том числе worker/scheduler и канал доставки.

Это отдельная эксплуатационная тема, а не часть базового создания Dashboard.

## Трек 6. API и автоматизация

Когда ручное создание и обслуживание объектов перестаёт масштабироваться, изучайте REST API Superset.

API подходит для:

- интеграций;
- автоматизации;
- управления объектами программно;
- собственных внутренних инструментов вокруг Superset.

Сначала нужно уверенно понимать сущности Superset через интерфейс. Иначе API только автоматизирует непонятную модель.

## Трек 7. Embedding

Если Dashboard должен быть частью другого веб-приложения или портала, отдельно изучайте embedding.

Это уже требует понимания:

- embedded configuration;
- allowed domains;
- guest token;
- аутентификации;
- прав доступа;
- безопасности внешнего приложения.

Не путайте embedding с обычной публикацией Dashboard внутри Superset.

# Рекомендуемый порядок следующего уровня

Если пока нет узкой задачи, разумный порядок такой:

```text
1. модель аналитических данных
2. SQL
3. роли и доступ к данным
4. Row Level Security
5. production architecture и security
6. backups и upgrades
7. caching / async / workers
8. Alerts & Reports
9. REST API
10. embedding
```

Почему так:

```text
сначала нужно правильно считать
        ↓
потом правильно ограничивать доступ
        ↓
потом надёжно эксплуатировать
        ↓
и только затем глубоко автоматизировать и встраивать
```

Это не единственно возможный порядок.

Если рабочая задача требует embedding прямо сейчас, соответствующий трек можно изучать раньше.

Но базовые знания источников, Dataset, Dashboard и доступа всё равно останутся фундаментом.

Если смешать их с первым знакомством, курс перестанет быть маршрутом для новичка и превратится в справочник администратора, аналитика и разработчика одновременно.
