# Шпаргалка к уроку 12. Форматы чисел, процентов и дат

Эта шпаргалка отвечает на практический вопрос:

> **как сделать результат читаемым, не изменив сами данные и смысл расчёта?**

Главное правило:

```text
значение
≠
формат отображения
```

Если число посчитано неправильно, формат не исправит расчёт.

Если число посчитано правильно, хороший формат помогает человеку быстро его прочитать.

---

## Самая короткая шпаргалка

| Исходное значение | Как хотим показать | Что меняется |
|---|---|---|
| `1234567.89` | `1 234 567,89` или аналог локали | только отображение |
| `0.253` | `25.3%` | только отображение при процентном формате |
| `25.3` | `25.3%` | сначала нужно понять смысл значения |
| `2026-08-25` | `25.08.2026` | формат даты |
| `2026-08-25 14:35:00` | `25.08.2026 14:35` | формат даты и времени |

---

# 1. Сначала проверьте само значение

Допустим, Metric вернула:

```text
0.253
```

Если смысл показателя:

```text
доля = 0.253
```

процентный формат может показать:

```text
25.3%
```

Но если SQL уже вернул:

```text
25.3
```

и это уже процентное значение, повторное процентное масштабирование может дать:

```text
2530%
```

Поэтому перед форматированием ответьте:

```text
в каком масштабе хранится и рассчитывается показатель?
```

---

# 2. Доля и процент — не одно и то же представление

Два распространённых соглашения:

```text
доля:
0.253

процент:
25.3
```

Оба варианта могут использоваться в данных.

Важно, чтобы команда использовала одно понятное правило.

Для BI удобно, когда Metric хранит математическую долю:

```text
0.253
```

а визуализация показывает:

```text
25.3%
```

Но это не обязательный универсальный стандарт. Главное — единообразие и понятная семантика.

---

# 3. Форматирование не должно жить в формуле без причины

Плохая идея для числовой Metric:

```sql
CONCAT(ROUND(..., 1), '%')
```

В результате получается строка.

Это может мешать:

```text
сортировке как числа
дальнейшим числовым операциям
повторному форматированию
использованию одного показателя в разных Chart
```

Предпочтительно:

```text
Metric возвращает число
        ↓
Chart отвечает за визуальный формат
```

---

# 4. Числовой формат

Во многих визуализациях Superset используются D3-style форматы чисел.

Точный набор полей настройки зависит от конкретного Chart.

Типичные задачи:

```text
число знаков после запятой
разделитель тысяч
проценты
компактное отображение больших значений
```

Примеры распространённых D3-format шаблонов:

```text
.0f   → без десятичных знаков
.2f   → два знака после запятой
,.2f  → разделитель тысяч + два знака
.1%   → процент с одним знаком
.2%   → процент с двумя знаками
```

Конкретный внешний вид разделителей зависит от настроенной локали.

---

# 5. Не показывайте лишнюю точность

Пример:

```text
1530.000000
```

если бизнес-смысл не требует шести знаков, такой вывод только создаёт шум.

Нормальнее:

```text
1530
```

или:

```text
1530.00
```

в зависимости от природы показателя.

Принцип:

```text
точность отображения
должна соответствовать точности бизнес-смысла
```

---

# 6. Деньги

Для денежных показателей обычно полезно:

```text
разделять тысячи
оставлять согласованное число десятичных знаков
явно указывать валюту, если она не очевидна
```

Например:

```text
1 234 567.89
```

или в другой локали:

```text
1 234 567,89
```

Не полагайтесь только на цвет или положение Chart, чтобы объяснить валюту.

Название показателя должно быть понятным:

```text
Выручка, ₽
```

или другой принятый в вашей документации вариант.

---

# 7. Количество объектов

Если показатель отвечает на вопрос:

> сколько документов?

и результат всегда целый, вывод:

```text
324.00
```

обычно хуже, чем:

```text
324
```

Не добавляйте десятичные знаки только потому, что поле в БД числовое.

---

# 8. Средние значения

Среднее часто требует десятичной точности.

Например:

```text
Среднее время = 3.428571 дня
```

для Dashboard можно показать:

```text
3.4 дня
```

Но не округляйте данные слишком рано внутри расчёта без необходимости.

Лучше:

```text
расчёт сохраняет точность
визуализация округляет отображение
```

---

# 9. Проценты

Перед настройкой `%` проверьте контрольный пример вручную.

Например:

```text
ошибок = 25
всего  = 100
```

Metric:

```sql
25.0 / 100.0
```

должна дать:

```text
0.25
```

После процентного форматирования ожидается:

```text
25%
```

Если получили:

```text
2500%
```

скорее всего, значение уже было умножено на 100 до форматирования.

---

# 10. Процент изменения и доля — разные показатели

Не путайте:

```text
доля ошибок
```

и:

```text
изменение ошибок относительно прошлого периода
```

Например:

```text
было 100
стало 120
```

изменение:

```text
+20%
```

Но доля некоторой категории внутри текущих 120 — это другой расчёт.

Одинаковый символ `%` не делает Metrics одинаковыми по смыслу.

---

# 11. Дата и время

У даты есть как минимум три разных вопроса:

```text
какое значение хранится?
какой период отбирается?
как дата показывается пользователю?
```

Это разные вещи.

Например:

```text
value      = 2026-08-25 14:35:00
Time range = August 2026
format     = 25.08.2026 14:35
```

→ [Time column, Time range и Time grain](05b-time-range-and-grain.md)

---

# 12. Time Grain не является форматом даты

```text
Time grain = Month
```

означает группировку времени по месяцам.

Это не просто косметическое превращение:

```text
2026-02-14
```

в:

```text
Февраль
```

Меняется зерно временного ряда.

То есть:

```text
Time grain
→ логика группировки

Time format
→ внешний вид подписи времени
```

Не путайте их.

---

# 13. Формат даты зависит от Chart

В разных визуализациях поле формата времени может находиться в разных настройках или использовать автоматический формат.

Superset имеет собственный слой time formatting на базе D3 time-format.

Поэтому правило курса:

```text
не заучивать расположение одного поля для всех Chart
```

а понимать смысл:

```text
временная агрегация
≠
формат подписи даты
```

---

# 14. Примеры D3 time-format

Типичные шаблоны:

```text
%Y       → год, например 2026
%m       → номер месяца
%d       → день месяца
%H       → час
%M       → минуты
%Y-%m-%d → 2026-08-25
%d.%m.%Y → 25.08.2026
%H:%M    → 14:35
```

Точный результат также зависит от контекста и локали.

Не используйте сложный формат, если автоматическое отображение уже читаемо.

---

# 15. Локаль

Одинаковое число может отображаться по-разному:

```text
1,234,567.89
```

и:

```text
1 234 567,89
```

Это вопрос локали и форматирования, а не разницы в числовом значении.

При сверке цифр сравнивайте значение, а не только строку, которую видите на экране.

---

# 16. Формат Table и формат Chart могут отличаться

Один Dataset может использоваться одновременно в:

```text
Big Number
Table
Bar Chart
Line Chart
```

В каждом Chart могут быть собственные настройки вывода.

Поэтому один и тот же Metric технически может выглядеть так:

```text
Table      → 1530.00
Big Number → 1.53k
Bar label  → 1,530
```

Число одно, визуальные форматы разные.

Для одного Dashboard лучше выбирать согласованный стиль, если нет причины делать иначе.

---

# 17. Компактные суффиксы

На больших значениях удобно сокращение:

```text
1 250 000
→ 1.25M
```

Но такая форма хуже для точной сверки.

Поэтому:

```text
KPI / обзор
→ компактный формат может быть удобен

детальная таблица / контроль
→ лучше точное число
```

Один Dashboard может использовать оба варианта для разных целей.

---

# 18. Не прячьте смысл в одном только формате

Плохо:

```text
25.3
```

без понятного названия — неизвестно, что это:

```text
рубли?
дни?
проценты?
литры?
коэффициент?
```

Хорошее название Metric или Chart должно помогать:

```text
Доля ошибок, %
Среднее время, дни
Выручка, ₽
Количество документов
```

---

# 19. Цвет не заменяет значение

Если KPI красный, пользователь всё равно должен понимать само число.

Плохо:

```text
красное 0.37
```

без подписи.

Лучше:

```text
Доля просроченных: 37%
```

а цвет использовать только как дополнительный сигнал.

---

# 20. Формат не исправляет неправильную Metric

Допустим, ожидается:

```text
25%
```

а Metric рассчитала:

```text
0.35
```

Можно сколько угодно менять число десятичных знаков, но правильного `25%` не появится.

Порядок диагностики:

```text
1. проверить исходные строки
2. проверить фильтры
3. проверить Metric
4. проверить агрегацию
5. получить контрольное числовое значение
6. только после этого настраивать формат
```

→ [Почему цифры в Superset не сходятся](07b-troubleshoot-wrong-numbers.md)

---

# 21. Простое корпоративное правило

Для одного Dashboard договоритесь заранее:

```text
деньги       → одинаковая точность
проценты     → одинаковая точность
количество   → без лишних десятичных
даты         → один понятный стиль
нулевые      → единообразно
NULL         → единообразно
```

Это делает Dashboard спокойнее и облегчает сверку.

---

# 22. Быстрый чек перед публикацией

Проверьте:

```text
[ ] Деньги выглядят как деньги?
[ ] Количества не имеют лишних .00?
[ ] Проценты не умножены на 100 дважды?
[ ] У процентов понятен смысл показателя?
[ ] Даты читаемы?
[ ] Time grain не перепутан с форматом даты?
[ ] Одинаковые Metrics оформлены одинаково?
[ ] Компактные K/M не мешают контрольной сверке?
[ ] Формат не скрывает аномально большое или маленькое значение?
```

---

# 23. Главное правило

```text
сначала правильное число
        ↓
потом правильная единица измерения
        ↓
потом удобный формат
```

Не наоборот.

Форматирование — последний слой представления результата.
