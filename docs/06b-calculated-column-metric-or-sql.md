# Шпаргалка к уроку 06. Calculated Column, Metric или SQL?

Эта шпаргалка отвечает на один практический вопрос:

> где должен жить расчёт?

В Superset похожий результат иногда можно получить несколькими способами. Но способы не равнозначны.

Самая короткая схема:

```text
Нужно вычислить значение для каждой строки?
→ Calculated Column

Нужно посчитать показатель по набору строк?
→ Metric

Нужно изменить сам набор данных, сделать JOIN, CTE, оконную функцию или сложную подготовку?
→ SQL / Virtual Dataset
```

---

## 1. Сначала определите уровень расчёта

Главное различие — не синтаксис SQL, а уровень данных.

```text
строка
→ Calculated Column

группа / набор строк
→ Metric

структура набора данных
→ SQL / Virtual Dataset
```

Это и есть основной выбор.

---

# 2. Calculated Column

Calculated Column — вычисляемое значение на уровне строки Dataset.

Пример из курса:

```sql
revenue - cost
```

Для каждой продажи получается собственное значение `profit`.

```text
строка 1:
200 - 120 = 80

строка 2:
450 - 280 = 170
```

После этого колонку можно агрегировать:

```text
SUM(profit)
AVG(profit)
MAX(profit)
```

---

## Когда Calculated Column подходит

Используйте, когда формула имеет смысл для одной записи.

Примеры:

```sql
revenue - cost
```

```sql
quantity * unit_price
```

```sql
CASE
  WHEN revenue > 1000 THEN 'large'
  ELSE 'small'
END
```

```sql
COALESCE(manager, 'Не указан')
```

То есть результат можно мысленно добавить как ещё один столбец к каждой строке.

---

## Когда Calculated Column не подходит

Если формула требует сначала собрать несколько строк вместе.

Например:

```sql
SUM(revenue)
```

или:

```sql
SUM(revenue) / COUNT(*)
```

это уже агрегированный расчёт.

Для него нужен Metric.

---

# 3. Metric

Metric отвечает на вопрос:

> что посчитать по текущему набору строк после фильтрации и группировки?

Пример из курса:

```sql
SUM(revenue) - SUM(cost)
```

Metric `Прибыль` работает по-разному в зависимости от группировки.

Без Dimension:

```text
все строки
→ 1530.00
```

С:

```text
Dimension = region
```

получаем:

```text
Север = 520.00
Юг    = 1010.00
```

Одна и та же Metric пересчитывается для каждой группы.

---

## Когда Metric подходит

Используйте для KPI и агрегированных показателей.

Примеры:

```sql
SUM(revenue)
```

```sql
COUNT(*)
```

```sql
COUNT(DISTINCT vehicle_id)
```

```sql
SUM(revenue) - SUM(cost)
```

```sql
SUM(profit) / NULLIF(SUM(revenue), 0)
```

Если результат должен меняться вместе с Filters и Dimensions, чаще всего речь о Metric.

---

# 4. SQL / Virtual Dataset

SQL нужен, когда задача уже не сводится к одному вычисляемому столбцу или одной агрегированной формуле.

Примеры:

```text
JOIN нескольких таблиц
CTE
оконные функции
ROW_NUMBER()
LAG() / LEAD()
сложная фильтрация
UNION
переименование и подготовка большого числа полей
изменение зерна набора данных
```

Тогда SQL определяет сам входной набор данных для Explore.

---

## Пример

Нужно присоединить справочник регионов:

```sql
SELECT
    s.sale_id,
    s.sale_date,
    s.region,
    r.region_group,
    s.revenue,
    s.cost
FROM training.sales s
LEFT JOIN training.regions r
    ON r.region = s.region
```

Это не Calculated Column и не Metric.

Появляется новая структура Dataset.

Значит нужен SQL — например Virtual Dataset или объект в самой базе.

---

# 5. Один вопрос — три разных уровня

Возьмём прибыль.

### Прибыль одной продажи

```sql
revenue - cost
```

→ `Calculated Column`

### Общая прибыль выбранных строк

```sql
SUM(revenue) - SUM(cost)
```

→ `Metric`

### Прибыль после сложной подготовки данных из нескольких таблиц

```sql
WITH ...
SELECT ...
JOIN ...
```

→ `SQL / Virtual Dataset`

Название показателя может быть одно и то же, но уровень расчёта разный.

---

# 6. Почему нельзя выбирать по принципу «где получилось написать формулу»

Технически SQL-выражение можно встретить в разных местах Superset.

Но вопрос должен быть:

> на каком уровне эта логика верна?

А не:

> в какое поле удалось вставить SQL?

Иначе легко получить расчёт, который выглядит правильно только на одном Chart, а при другой группировке начинает давать другой смысл.

---

# 7. Хороший порядок выбора

```text
1. Можно ли вычислить значение у одной строки?
   Да → Calculated Column

2. Нужно ли получить показатель по группе строк?
   Да → Metric

3. Нужно ли изменить сам входной набор данных?
   Да → SQL / Virtual Dataset
```

---

# 8. Calculated Column + Metric могут работать вместе

Это нормальный сценарий.

Например:

```text
Calculated Column:
profit = revenue - cost
```

а затем Metric:

```text
SUM(profit)
```

То есть:

```text
строка
→ вычисляем profit

группа
→ суммируем profit
```

В учебных данных это даёт тот же итог, что:

```sql
SUM(revenue) - SUM(cost)
```

Но это не значит, что Calculated Column и Metric являются одним объектом.

---

# 9. Когда лучше сохранить Metric в Dataset

Если показатель нужен повторно в нескольких Chart, лучше создать сохранённую Metric в Dataset.

Плюсы:

```text
единое определение
одинаковый Label
повторное использование
меньше риска написать формулу по-разному в разных Chart
```

Ad hoc Metric полезна для разовой проверки и исследования.

Для корпоративного KPI лучше иметь одно контролируемое определение.

---

# 10. Когда Virtual Dataset уже недостаточно

Virtual Dataset удобен для аналитической подготовки SQL внутри Superset.

Но не вся подготовка данных должна жить там.

Если логика:

- тяжёлая;
- используется многими системами;
- должна рассчитываться централизованно;
- требует регулярного materialization;
- является частью корпоративной модели данных;

то её разумнее вынести в БД или ETL/ELT-процесс:

```text
VIEW
Materialized View
таблица-витрина
модель dbt / другой слой трансформаций
```

Superset должен читать удобный аналитический набор, а не обязательно выполнять всю инженерную подготовку сам.

---

# 11. JOIN — почти всегда уровень SQL

Если нужно связать таблицы:

```text
продажи
+
справочник менеджеров
```

это изменение набора данных.

Значит:

```text
SQL / VIEW / Virtual Dataset
```

а не Calculated Column.

При JOIN обязательно проверяйте зерно и размножение строк.

Если одна строка `sales` совпала с тремя строками справочника, сумма продаж может утроиться.

---

# 12. Оконные функции — SQL

Примеры:

```sql
ROW_NUMBER() OVER (...)
LAG(...) OVER (...)
LEAD(...) OVER (...)
SUM(...) OVER (...)
```

Это логика, зависящая от набора строк и их порядка.

Для такого расчёта используйте SQL-подготовку.

---

# 13. CASE может встречаться в разных местах

Сам `CASE` не определяет уровень расчёта.

Построчный CASE:

```sql
CASE
  WHEN revenue >= 500 THEN 'Крупная'
  ELSE 'Обычная'
END
```

→ Calculated Column.

CASE внутри агрегирования:

```sql
SUM(
  CASE
    WHEN region = 'Север' THEN revenue
    ELSE 0
  END
)
```

→ Metric.

Смотрите на смысл расчёта, а не на ключевое слово.

---

# 14. Быстрая таблица выбора

| Задача | Где делать |
|---|---|
| `revenue - cost` для каждой строки | Calculated Column |
| категория строки через `CASE` | Calculated Column |
| `SUM(revenue)` | Metric |
| `COUNT(DISTINCT manager)` | Metric |
| маржа по выбранной группе | Metric |
| JOIN таблиц | SQL / Virtual Dataset |
| CTE | SQL / Virtual Dataset |
| оконная функция | SQL / Virtual Dataset |
| UNION нескольких источников | SQL / Virtual Dataset |
| тяжёлая общая витрина для многих систем | чаще БД / ETL |

---

# 15. Типовые ошибки

## Агрегат записан как Calculated Column

Проблемный смысл:

```sql
SUM(revenue)
```

Calculated Column должен описывать значение строки, а не итог группы.

---

## Построчную логику дублируют во всех Chart

Если одно выражение постоянно используется как новое поле, лучше вынести его в Calculated Column или ещё ниже — в модель данных.

---

## Один KPI написан по-разному в разных Chart

Например:

```text
Chart A → SUM(profit)
Chart B → SUM(revenue) - SUM(cost)
Chart C → ещё одна версия формулы
```

Если это один корпоративный показатель, лучше определить одну сохранённую Metric и использовать её повторно.

---

## Весь SQL запихнули в Virtual Dataset, хотя нужна одна формула

Если исходный Dataset уже правильный и нужна только простая построчная колонка, Virtual Dataset может быть лишним усложнением.

---

# 16. Контрольный вопрос перед созданием расчёта

Спросите себя:

```text
Что является одной строкой моего Dataset?
```

После этого:

```text
расчёт относится к этой одной строке?
→ Calculated Column

расчёт относится к группе таких строк?
→ Metric

нужно изменить, какие строки и столбцы вообще входят в Dataset?
→ SQL / Virtual Dataset
```

Если на первый вопрос про одну строку ответить нельзя, сначала нужно разобраться с зерном данных.

---

# 17. Главное правило

```text
Calculated Column
→ вычисляет атрибут строки

Metric
→ вычисляет показатель группы

SQL / Virtual Dataset
→ формирует набор данных
```

Это не три конкурирующих способа написать одну и ту же формулу. Это три разных уровня аналитической модели.
