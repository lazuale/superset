# 01. Что такое Apache Superset

## Что научимся делать

После этого урока вы должны понимать:

- для чего нужен Apache Superset;
- где находятся сами данные, а где начинается работа Superset;
- какие задачи Superset решает нативно;
- где проходит граница между аналитикой в Superset и подготовкой данных в базе;
- когда сложный расчёт в Superset уместен, а когда это уже плохая архитектура;
- что означают `Database`, `Dataset`, `Explore`, `Metric`, `Chart`, `Dashboard` и `SQL Lab`;
- как эти сущности связаны между собой;
- какой путь мы пройдём дальше в курсе.

В этом уроке ничего устанавливать и настраивать не нужно. Задача одна: сначала понять общую картину, чтобы следующие действия в интерфейсе не выглядели набором случайных кнопок.

## Что нужно до начала

Ничего.

Не требуется знать SQL, Docker, PostgreSQL или устройство Superset.

## На пальцах: что такое Superset

Apache Superset — это веб-приложение для исследования данных, построения визуализаций и аналитических панелей.

Самый простой сценарий выглядит так:

```text
данные уже находятся в базе
        ↓
Superset подключается к базе
        ↓
вы выбираете источник данных
        ↓
задаёте вопрос к данным
        ↓
получаете таблицу или график
        ↓
сохраняете график
        ↓
собираете графики в Dashboard
```

Главное, что нужно понять сразу: **Superset не является хранилищем ваших бизнес-данных**.

Если продажи лежат в PostgreSQL, то строки продаж продолжают лежать в PostgreSQL. Superset подключается к этой базе и обращается к ней за данными, необходимыми для анализа и визуализации.

В нашем учебном курсе данные будут находиться в PostgreSQL в таблице:

```text
training.sales
```

Superset будет работать с этой таблицей, но не станет её заменой.

## Для чего Superset может понадобиться

Superset полезен не только для того, чтобы «нарисовать график».

Его основная область — **интерактивная BI-аналитика данных, которые уже доступны в SQL-источнике**.

Ниже несколько типовых сценариев.

### Сценарий 1. Быстро посмотреть состояние показателей

Например, нужно видеть:

```text
общую выручку
количество операций
среднее значение
динамику по времени
распределение по регионам
```

Для этого можно собрать несколько `Chart` и объединить их в один `Dashboard`.

Пользователю не нужно каждый раз открывать таблицу и пересчитывать показатели вручную.

### Сценарий 2. Исследовать данные вопрос за вопросом

Например:

> В каком регионе показатель выше?

Затем:

> А если оставить только текущий год?

Затем:

> А как выглядит результат по месяцам?

Такие вопросы удобно разбирать в `Explore`: менять группировки, метрики, фильтры и представление данных без создания отдельного отчёта под каждый вопрос.

### Сценарий 3. Сделать единый интерактивный Dashboard

Например:

```text
Dashboard
├── общий показатель
├── динамика по месяцам
├── распределение по категориям
└── детальная таблица
```

Фильтр Dashboard может позволить выбрать период, регион или категорию и применить выбор сразу к нескольким графикам.

### Сценарий 4. Выполнить собственный SQL-анализ

Если возможностей визуального конструктора недостаточно, в `SQL Lab` можно написать SQL-запрос вручную.

Например:

```sql
SELECT
    region,
    SUM(revenue) AS revenue
FROM training.sales
GROUP BY region
ORDER BY revenue DESC;
```

`SQL Lab` позволяет использовать возможности SQL той базы данных, к которой подключён Superset.

Это важно: **сложный анализ в Superset возможен, но сами SQL-вычисления выполняет подключённая база данных или другой SQL-движок, а не браузер пользователя**.

### Сценарий 5. Сохранить общий способ расчёта показателя

В `Dataset` можно определить вычисляемые поля и метрики, а затем использовать их в разных визуализациях.

Например, вместо того чтобы каждый раз заново вспоминать выражение:

```sql
SUM(revenue)
```

можно определить метрику с понятным названием и использовать её в нескольких `Chart`.

Это часть лёгкого semantic layer Superset: общие аналитические определения можно хранить рядом с `Dataset`, а не копировать вручную в каждую визуализацию.

## Где проходит граница применения

У Superset нет жёсткой границы вида «можно только простые графики».

Он умеет работать и с простыми таблицами, и со сложными SQL-запросами. Но важно различать две вещи:

1. **можно ли технически выполнить задачу**;
2. **правильно ли держать эту задачу именно в Superset**.

Удобная начальная модель выглядит так:

| Задача | Где ей обычно место | Оценка для Superset |
|---|---|---|
| Таблица, график, KPI, Dashboard | Superset | нативно |
| Фильтрация и группировка | Superset | нативно |
| `SUM`, `COUNT`, `AVG`, доли и другие аналитические метрики | Superset / SQL источника | нативно |
| Вычисляемое поле для анализа | Dataset | нативно |
| SQL-запрос аналитика | SQL Lab | нативно |
| Virtual Dataset на SQL-запросе | Superset | нативно |
| `JOIN`, CTE, оконные функции и сложный SQL | SQL Lab / Virtual Dataset / база данных | допустимо, зависит от задачи |
| Постоянная сложная логика, которой пользуются много отчётов | представление, таблица или витрина в базе данных | лучше вынести из Superset |
| Очистка, нормализация и регулярная подготовка сырых данных | система подготовки данных / база данных | не основная задача Superset |
| Хранение исходных бизнес-данных | исходная система / база данных | не задача Superset |
| Ручное редактирование рабочих записей пользователями | прикладная система | не типовой сценарий Superset |
| Согласования, задачи и бизнес-процессы | специализированная система | не задача Superset |

Эта таблица не означает, что Superset «не умеет считать».

Она показывает **границу ответственности**.

## Может ли Superset выполнять сложный анализ

Да.

Например, аналитик может написать в `SQL Lab` запрос с:

```text
JOIN
CTE
CASE
оконными функциями
агрегациями
подзапросами
```

Если подключённая база данных поддерживает такой SQL и у пользователя есть необходимые права, запрос может быть выполнен.

Условно:

```text
SQL Lab
   ↓
сложный SQL-запрос
   ↓
база данных выполняет расчёт
   ↓
Superset получает результат
   ↓
таблица / Chart / Dashboard
```

Поэтому утверждение «Superset нужен только для визуализации готовых чисел» слишком узкое.

Правильнее сказать так:

> Superset позволяет исследовать данные, определять аналитические метрики, выполнять SQL-запросы и визуализировать результат, но основная тяжёлая обработка выполняется подключённым SQL-источником.

## Когда сложный SQL в Superset — это нормально

Сложность запроса сама по себе ещё не делает решение плохим.

Например, для разового исследования аналитик может написать запрос:

```text
несколько таблиц
      ↓
JOIN
      ↓
агрегация
      ↓
результат
```

и проверить гипотезу в `SQL Lab`.

Если результат нужен для дальнейшей визуализации, запрос можно сохранить как `Virtual Dataset`.

Это штатный сценарий.

## Когда начинается архитектурный костыль

Проблема начинается не тогда, когда запрос длинный, а тогда, когда Superset становится местом постоянной подготовки и определения самих бизнес-данных.

Например:

```text
сырые таблицы
    ↓
очистка
    ↓
нормализация
    ↓
JOIN множества источников
    ↓
десятки бизнес-правил
    ↓
определение статусов
    ↓
расчёт итоговой сущности
    ↓
Dashboard
```

Если вся эта логика постоянно хранится внутри одного большого `Virtual Dataset`, который затем используется как основа многих отчётов, решение становится труднее проверять, переиспользовать и сопровождать.

Обычно устойчивее подготовить результат в самой аналитической базе:

```text
сырые данные
    ↓
подготовка в базе данных
    ↓
таблица / VIEW / аналитическая витрина
    ↓
Dataset
    ↓
Superset
```

Тогда Superset занимается тем, в чём особенно силён:

```text
исследование
метрики
фильтры
сравнения
визуализация
dashboards
SQL-анализ
```

а повторяемая тяжёлая подготовка данных остаётся ниже по архитектуре.

## Простое правило для новичка

Если задача звучит примерно так:

> **Как посчитать, сгруппировать, отфильтровать, сравнить и показать уже доступные данные?**

Superset, скорее всего, подходит хорошо.

Если задача звучит так:

> **Как получить правильные исходные данные из нескольких сырых систем, очистить их, исправить, нормализовать и сохранить результат как новую рабочую сущность?**

это уже задача подготовки данных, а Superset лучше подключать после неё.

Можно запомнить ещё короче:

```text
база данных отвечает:
что за данные мы подготовили

Superset отвечает:
как их исследовать, посчитать и показать
```

Это не абсолютный технический запрет, а хорошая архитектурная граница.

## Что Superset делает

Для обычного пользователя Superset решает несколько основных задач.

### 1. Подключается к базе данных

Superset должен знать, где находится база и как к ней подключиться.

В интерфейсе такое подключение представлено сущностью `Database`.

На практике это означает: Superset получает адрес сервера, имя базы, пользователя и другие параметры, после чего может выполнять разрешённые запросы к источнику данных.

Подключение к PostgreSQL мы сделаем в уроке 03.

### 2. Даёт выбрать данные для анализа

После подключения базы нужно определить, с каким источником мы будем работать.

Для этого используется `Dataset` — набор данных Superset.

В начале курса всё будет максимально просто:

```text
PostgreSQL
└── schema training
    └── table sales
            ↓
        Dataset в Superset
```

То есть мы зарегистрируем существующую таблицу `training.sales` как `Dataset`.

Важно: создание `Dataset` **не означает копирование всей таблицы в Superset**. Это подготовка источника для дальнейшей работы в интерфейсе Superset.

Позже мы познакомимся и с `Virtual Dataset` — набором данных, который строится на SQL-запросе. Но до него дойдём только после знакомства с `SQL Lab`.

### 3. Позволяет исследовать данные без написания SQL

Основной рабочий экран для такого анализа называется `Explore`.

В `Explore` можно выбрать:

- какие поля использовать;
- по чему группировать данные;
- какую метрику считать;
- какие фильтры применить;
- какой период взять;
- какой тип визуализации построить.

Например, вопрос:

> Какая выручка была по каждому региону?

можно собрать в `Explore` примерно так:

```text
группировка: region
метрика: SUM(revenue)
```

После запуска анализа Superset получает результат для визуализации и показывает его в выбранном виде.

Подробно `Explore` разберём в уроке 05.

## Основные сущности, которые нужно различать

На первом этапе достаточно семи понятий.

### `Database`

Это подключение Superset к базе данных.

Не сама таблица и не сами данные, а настроенный доступ к источнику.

В нашем курсе это будет подключение к учебному PostgreSQL.

### `Dataset`

Это источник данных, подготовленный для работы в Superset.

В простейшем случае `Dataset` связан с обычной таблицей базы данных.

Наш первый `Dataset` будет основан на:

```text
training.sales
```

### `Explore`

Это рабочий экран, где вы исследуете `Dataset` и собираете запрос через элементы интерфейса.

Здесь выбираются группировки, метрики, фильтры, период и тип визуализации.

`Explore` можно воспринимать как конструктор аналитического запроса и визуализации без необходимости сразу писать SQL вручную.

### `Metric`

`Metric` — это вычисляемый показатель.

Например:

```text
сумма выручки
количество продаж
средняя выручка
```

В SQL такие показатели часто выражаются агрегатными функциями:

```sql
SUM(revenue)
COUNT(*)
AVG(revenue)
```

Пока достаточно понимать смысл: **поле хранит данные, а Metric отвечает на вопрос «что посчитать?»**.

Метрики подробно разберём в уроке 06.

### `Chart`

`Chart` — сохранённая визуализация в Superset.

Это не просто картинка.

У сохранённого `Chart` есть источник данных, выбранный тип визуализации, метрики, группировки, фильтры и другие настройки.

Например, один `Chart` может показывать:

```text
выручку по регионам
```

а другой:

```text
динамику выручки по месяцам
```

Оба могут использовать один и тот же `Dataset`.

### `Dashboard`

`Dashboard` — панель, на которой размещаются сохранённые `Chart`.

Например:

```text
Dashboard: Продажи

├── общая выручка
├── выручка по регионам
├── продажи по продуктам
└── динамика выручки по времени
```

На Dashboard можно собрать несколько взглядов на одну тему и позже добавить общие фильтры.

### `SQL Lab`

`SQL Lab` — встроенный интерфейс для работы с SQL.

В нём можно выбрать подключённую базу, написать SQL-запрос, выполнить его и посмотреть результат.

Например:

```sql
SELECT region, SUM(revenue)
FROM training.sales
GROUP BY region;
```

К этому моменту курса SQL уже не будет выглядеть чем-то отдельным от `Explore`: мы увидим, что один и тот же аналитический вопрос можно решать разными способами.

`SQL Lab` изучим в уроке 10.

## Как всё связано

Основной путь можно представить так:

```text
PostgreSQL
    │
    │ хранит строки данных
    ▼
Database
    │
    │ подключение Superset к PostgreSQL
    ▼
Dataset
    │
    │ источник для анализа
    ▼
Explore
    │
    │ группировки + метрики + фильтры
    ▼
Chart
    │
    │ сохранённая визуализация
    ▼
Dashboard
    │
    └── несколько Chart + фильтры
```

`SQL Lab` идёт рядом с этим путём:

```text
PostgreSQL
    ▲
    │ SQL-запрос
    │
SQL Lab
```

А позже мы свяжем оба маршрута:

```text
SQL Lab
   ↓
SQL-запрос
   ↓
Virtual Dataset
   ↓
Explore
   ↓
Chart
```

## Что Superset не делает

Чтобы дальше не возникало неправильных ожиданий, сразу зафиксируем границы.

### Superset не заменяет базу данных

Если исходные данные находятся в PostgreSQL, PostgreSQL остаётся местом их хранения.

### Superset не является системой подготовки данных

Superset может выполнять аналитические SQL-запросы, но регулярную загрузку, очистку, нормализацию и объединение сырых источников лучше не превращать в цепочку огромных `Virtual Dataset`.

Если одна и та же сложная подготовка постоянно нужна множеству отчётов, обычно лучше подготовить таблицу, представление или аналитическую витрину в самой базе данных.

### Superset не является системой ручного ведения данных

Основной пользовательский сценарий Superset — читать и анализировать данные.

Если пользователям нужно создавать рабочие записи, редактировать карточки, менять статусы, согласовывать заявки или вести процесс исполнения, для этого нужна прикладная система, а Superset может использовать её данные для аналитики.

### Superset не исправляет плохие данные автоматически

Если в источнике неверные суммы, дубли или неправильные даты, красивый график не сделает эти данные правильными.

### Superset не превращает любой набор данных в хорошую аналитику автоматически

Нужно понимать, какой вопрос вы задаёте, какое поле используете для группировки и какой показатель считаете.

Именно поэтому в курсе мы будем постоянно проверять результат на маленькой таблице, где значения можно пересчитать вручную.

### Superset не требует SQL для каждого действия

Для большого количества обычных задач достаточно `Explore`.

SQL становится нужен тогда, когда удобнее или необходимо явно написать запрос. Поэтому сначала мы освоим визуальный путь без написания SQL, а `SQL Lab` появится только в уроке 10.

## Пример одного аналитического вопроса

Представим, что в PostgreSQL есть такие строки:

| Регион | Выручка |
|---|---:|
| Север | 100 |
| Север | 150 |
| Юг | 200 |

Нас интересует вопрос:

> Сколько выручки приходится на каждый регион?

В Superset логика будет такой:

```text
Dataset: training.sales

Group By:
region

Metric:
SUM(revenue)
```

Ожидаемый результат:

| Регион | Выручка |
|---|---:|
| Север | 250 |
| Юг | 200 |

Дальше этот же результат можно показать таблицей, столбчатой диаграммой или использовать внутри Dashboard.

Смысл Superset не в том, что он «рисует графики», а в том, что он связывает источник данных, аналитический запрос и визуальное представление результата в одном рабочем интерфейсе.

## Что произошло бы внутри Superset

Пока без технических деталей достаточно такой модели:

1. вы выбираете `Dataset`;
2. задаёте параметры анализа в `Explore`;
3. Superset получает необходимые данные для визуализации; в обычном случае для этого выполняется запрос к источнику данных;
4. результат отображается как таблица или график;
5. при сохранении создаётся `Chart`, который можно использовать снова и добавить в `Dashboard`.

В дальнейшем мы увидим дополнительные механизмы, которые могут влиять на получение результата, но для первого рабочего сценария их знать не нужно.

Нам пока также не нужно знать устройство сервера Superset, внутренней базы или фоновых процессов.

## Попробуйте объяснить своими словами

До следующего урока проверьте, можете ли вы без подсказки ответить на восемь вопросов.

1. Где физически находятся строки `training.sales` — в Superset или PostgreSQL?
2. Для чего нужен `Dataset`?
3. Чем `Explore` отличается от `Chart`?
4. Что собирает несколько `Chart` на одной странице?
5. Для чего нужен `SQL Lab`?
6. Может ли Superset выполнять сложный SQL-анализ?
7. Кто обычно выполняет основную тяжёлую обработку SQL — Superset или подключённая база данных?
8. Где лучше держать постоянную сложную подготовку данных, которой пользуются несколько отчётов?

Правильная общая картина должна выглядеть так:

```text
данные хранятся и подготавливаются в SQL-источнике
        ↓
Superset подключается к источнику
        ↓
Dataset определяет данные для анализа
        ↓
Explore или SQL Lab задают аналитический вопрос
        ↓
Chart сохраняет визуализацию
        ↓
Dashboard объединяет Chart
```

Если эта цепочка и граница ответственности понятны, урок выполнен.
