# 05. Осваиваем Explore

## Что научимся делать

После этого урока вы должны уметь:

- открыть `Explore` для существующего Dataset;
- понимать, что именно настраивается в `Explore`;
- получить агрегированный результат без написания SQL;
- использовать `Dimensions`;
- создать простую временную `ad hoc metric` прямо в `Explore`;
- применять фильтры через `Filters`;
- задать временной диапазон для `sale_date`;
- понимать включённую и исключённую границы пользовательского диапазона;
- понимать, когда появляется и зачем нужен `Time grain`;
- сгруппировать даты по месяцам;
- ограничить число возвращаемых строк через `Row limit`;
- выполнять текущую конфигурацию через `Create chart`;
- прочитать результат и проверить его по контрольным значениям;
- изменить условие и повторно выполнить тот же аналитический запрос.

В этом уроке мы **не создаём сохранённые Metrics, Calculated Columns и не сохраняем Chart**.

Наша задача — научиться задавать простой аналитический вопрос через `Explore` и понимать, как настройки превращаются в результат.

## Какой вопрос будем решать

Начнём с конкретного вопроса:

> Какая суммарная выручка приходится на каждый регион?

В таблице `training.sales` есть:

```text
region
revenue
```

Чтобы ответить на вопрос, нужно:

1. разделить строки по `region`;
2. сложить `revenue` внутри каждого региона.

В интерфейсе `Table` Superset 6.1.0 это собирается так:

```text
region
   │
   └── Dimensions

revenue
   │
   └── Metrics → SUM
```

SQL для этого писать не будем. Эту конструкцию соберём через `Explore`.

Перейдите в самостоятельный раздел:

```text
Datasets
```

Найдите Dataset:

```text
sales
```

Нажмите на его имя.

Откроется `Explore`.

Слева должен быть выбран Dataset `sales`, а в списке его полей должны присутствовать:

```text

```

Если открылся другой Dataset, не продолжайте: вернитесь в `Datasets` и снова откройте `sales`.

## Что такое Explore

`Explore` — основной визуальный конструктор аналитического запроса в Superset.

Здесь мы выбираем:

```text
из какого Dataset брать данные
        ↓
по каким измерениям разделить результат
        ↓
что считать
        ↓
какие строки отфильтровать
        ↓
как обработать время
        ↓
в каком виде показать результат
```

После запуска текущей конфигурации Superset формирует запрос к источнику данных и получает результат из PostgreSQL.

Важно:

```text
Explore ≠ отдельная копия данных
Explore ≠ Excel-лист
Explore ≠ SQL Lab
```

Мы задаём параметры запроса через интерфейс, а данные остаются в PostgreSQL.

## Выполняем конфигурацию Explore

Для нового, ещё не сохранённого Chart текущая конфигурация выполняется кнопкой:

```text
Create chart
```

После сохранения Chart эта кнопка будет называться:

```text
Update chart
```

В этом уроке Chart ещё не сохранён, поэтому после изменения параметров нажимаем:

```text
Create chart
```

`Create chart` выполняет текущую конфигурацию и обновляет результат на экране. Сохранение Chart как отдельного объекта выполняется через `Save`; это разберём в уроке 07.

## Выбираем Table

Для первого упражнения используем визуализацию:

```text
Table
```

Если `Table` уже выбрана, ничего менять не нужно.

Если выбран другой тип визуализации, нажмите на текущий тип визуализации и выберите:

```text
Table
```

В секции `Query` доступны, среди прочего:

```text
Query mode
Dimensions
Metrics
Percentage metrics
Filters
Sort query by
Server pagination
Row limit
```

Эти элементы используем дальше.

## Сначала проверяем Filters

В `Table` временной диапазон задаётся через секцию:

```text
Filters
```

На новом Chart там может уже отображаться temporal-фильтр вроде:

```text
sale_date (No filter)
```

Если он есть, оставьте:

```text
No filter
```

Если temporal-фильтр ещё не добавлен, отдельного ограничения по дате сейчас нет — это тоже подходит для первого запроса.

Наши фиксированные учебные данные находятся в периоде:

```text
2026-01-05 … 2026-03-24
```

Для учебных данных используем `No filter` или конкретные даты 2026 года.

## Настраиваем Dimensions

В секции `Query` найдите:

```text
Dimensions
```

Добавьте столбец:

```text
region
```

Это означает:

```text
разделить результат по значениям region
```

В наших данных существуют два значения:

```text
Север
Юг
```

Поэтому итоговая таблица должна содержать две группы.

`Dimensions` — подпись поля интерфейса `Table`. На уровне SQL эта настройка соответствует группировке по `region`, то есть концептуально:

```sql
GROUP BY region
```

## Добавляем временную метрику SUM(revenue)

Найдите:

```text
Metrics
```

Добавьте столбец:

```text
revenue
```

Для агрегирования выберите:

```text
SUM
```

Итоговая временная метрика должна означать:

```text
SUM(revenue)
```

Она отвечает на вопрос:

> сколько всего выручки находится внутри каждого значения Dimension?

### Почему это пока не сохранённая Metric

Сейчас мы создаём **ad hoc metric** — разовый расчёт внутри текущего Explore.

Он нужен для конкретного запроса и пока не становится постоянным элементом Dataset.

То есть сейчас:

```text
Explore
└── временный SUM(revenue)
```

А в следующем уроке будет другой уровень:

```text
Dataset
└── сохранённая Metric
```

Разницу между временной и сохранённой метрикой подробно разберём в уроке 06.

## Устанавливаем Row limit

Найдите:

```text
Row limit
```

Для учебного запроса можно установить:

```text
100
```

Здесь вернутся только две строки, потому что у нас всего два региона.

`Row limit` задаёт верхнюю границу количества строк результата, которые Superset запрашивает для этой визуализации.

Это не означает:

```text
взять первые 100 строк training.sales и только потом посчитать результат
```

Для агрегированного запроса ограничивается уже результирующий набор групп.

## Запускаем первый запрос

Проверьте основную конфигурацию:

```text
Visualization: Table
Dimensions:    region
Metrics:       SUM(revenue)
Filters:       без активного ограничения
Row limit:     100
```

Если в `Filters` отображается `sale_date`, его состояние должно быть:

```text
No filter
```

Нажмите:

```text
Create chart
```

## Контрольный результат

Должны получиться две строки:

| region | SUM(revenue) |
|---|---:|
| Север | 1360.00 |
| Юг | 2645.00 |

Порядок строк может отличаться.

Главная проверка:

```text
Север = 1360.00
Юг    = 2645.00
```

Их сумма:

```text
1360.00 + 2645.00 = 4005.00
```

Это совпадает с общей контрольной выручкой учебного набора из урока 02:

```text
revenue = 4005.00
```

Если числа совпали, вы впервые получили проверяемый агрегированный результат через `Explore`.

## Что сейчас сделал Superset

Мы настроили интерфейс так:

```text
Dimensions = region
Metrics    = SUM(revenue)
```

По смыслу запрос близок к:

```sql
SELECT
    region,
    SUM(revenue)
FROM training.sales
GROUP BY region;
```

Superset может сгенерировать технически более сложный SQL, чем этот пример. Сейчас важно понять саму логику:

```text
Dimensions → определяет разбиение результата
Metrics    → определяет расчёт внутри каждой группы
```

## Сортируем результат

В полученной таблице нажмите на заголовок столбца с `SUM(revenue)`.

Добейтесь сортировки по убыванию.

Первой строкой должен стать:

```text
Юг    2645.00
```

второй:

```text
Север 1360.00
```

Повторное нажатие на заголовок меняет направление сортировки.

Не путайте сортировку уже отображённой таблицы с `Dimensions`: сортировка меняет порядок строк результата, но не меняет сами группы и их значения.

## Добавляем обычный фильтр

Теперь ответим на более узкий вопрос:

> Какая суммарная выручка у региона Север?

В секции `Query` найдите:

```text
Filters
```

Добавьте фильтр по столбцу:

```text
region
```

Условие должно оставить только значение:

```text

```

В зависимости от доступного оператора это может выглядеть как равенство или выбор значения из списка.

После этого снова выполните запрос кнопкой:


Теперь должна остаться одна группа:

|---|---:|
| Север | 1360.00 |

Сначала `Filters` ограничил строки, участвующие в запросе, затем `Dimensions` и `SUM(revenue)` сформировали результат по оставшимся данным.

## Задаём временной диапазон через Filters

Для Dataset `sales` временным столбцом является:

```text
sale_date
```

Теперь ограничим результат только февралем 2026 года.

В секции:

```text
Filters
```

откройте существующий temporal-фильтр `sale_date` или добавьте фильтр по `sale_date`, если его ещё нет.

Для временного условия выберите пользовательский (`Custom`) диапазон.

В Superset 6.1.0 границы пользовательского диапазона подписаны так:

```text
Start (inclusive)
End (exclusive)
```

Чтобы взять **весь февраль 2026 года**, задайте:

```text
Start (inclusive): 2026-02-01
End (exclusive):   2026-03-01
```

Логическое условие получается таким:

```text
2026-02-01 <= sale_date < 2026-03-01
```

Не ставьте `End = 2026-02-28`: поскольку End является exclusive, такая граница исключит весь день 28 февраля.

Примените значение фильтра и выполните запрос кнопкой:

```text
Create chart
```

Конфигурация по-прежнему должна содержать:

```text
Dimensions = region
Metrics    = SUM(revenue)
```

Контрольные значения за февраль:

| region | SUM(revenue) |
|---|---:|
| Север | 450.00 |
| Юг | 730.00 |

Итого:

```text
1180.00
```

После проверки верните temporal-фильтр `sale_date` в состояние:

```text
No filter
```

или удалите его, если он был добавлен только для упражнения.

Снова выполните запрос.

Должны вернуться исходные значения:

```text
Север = 1360.00
Юг    = 2645.00
```

## Почему контрольные данные не заменяют понимание границ

В текущем учебном наборе последняя февральская продажа датирована 27 февраля.

Поэтому ошибочная верхняя граница `2026-02-28` случайно могла бы дать те же контрольные суммы.

Это не делает её правильной.

Для календарного месяца используем устойчивую модель:

```text
первый день месяца включительно
→ первый день следующего месяца исключительно
```

Например:

```text
февраль 2026
2026-02-01 <= sale_date < 2026-03-01
```

Эта модель останется корректной и тогда, когда в данных появятся строки за 28 февраля или время внутри суток.

## Фиксированный и относительный временной фильтр

Временной фильтр Superset умеет работать как с фиксированными датами, так и с относительными выражениями времени.

Примеры относительных диапазонов:

```text
Last 7 days
Last month
Last quarter
Last year
```

Их смысл зависит от момента выполнения запроса.

Например:

```text
Last month
```

сегодня и через месяц будет означать разные календарные интервалы.

Поэтому в учебном наборе с фиксированными историческими датами используем либо:

```text
No filter
```

либо конкретные даты 2026 года.

Так результаты урока остаются воспроизводимыми.

## Временной диапазон и Time grain — не одно и то же

Эти две настройки часто путают.

Temporal filter в `Filters` отвечает:

```text
какой период данных взять?
```

`Time grain` отвечает:

```text
с какой временной детализацией сгруппировать временное измерение?
```

Например:

```text
Filters: sale_date = январь–март 2026
Time grain: Month
```

означает:

```text
взять данные за январь–март
и собрать даты в месячные группы
```

Сам по себе `Time grain` не задаёт период отбора.

## Смотрим Time grain на практике

В нашей первой таблице временное поле не участвовало в `Dimensions`, поэтому `Time grain` там не был нужен.

Теперь зададим другой вопрос:

> Как менялась общая выручка по месяцам?

Оставьте визуализацию:

```text
Table
```

Удалите `region` из `Dimensions` и добавьте:

```text
sale_date
```

Поскольку выбран временной столбец, в Query становится применим `Time grain`.

Установите:

```text
Dimensions: sale_date
Time grain: Month
Metrics:    SUM(revenue)
```

В `Filters` не должно быть активного ограничения по дате. Если отображается temporal-фильтр `sale_date`, оставьте:

```text
No filter
```

Выполните текущую конфигурацию кнопкой:

```text
Create chart
```

## Контроль по месяцам

Должны получиться три временные группы:

| месяц | SUM(revenue) |
|---|---:|
| 2026-01 | 1160.00 |
| 2026-02 | 1180.00 |
| 2026-03 | 1665.00 |

Проверка общей суммы:

```text
1160.00 + 1180.00 + 1665.00 = 4005.00
```

Теперь смысл `Time grain = Month` можно увидеть непосредственно:

```text
12 отдельных дат продаж
        ↓
Dimensions = sale_date
        ↓
Time grain = Month
        ↓
3 группы
├── 2026-01
├── 2026-02
└── 2026-03
```

Если выбрать более мелкую временную детализацию, групп станет больше. Если более крупную — меньше.

Пока не перебирайте все варианты `Time grain`. Важно понять принцип.

## Как читать запрос Explore

Для простого агрегированного запроса `Table` удобно мыслить в таком порядке:

```text
1. Dataset
   Что является источником?

2. Filters
   Какие строки и какой период оставляем?

3. Dimensions
   По каким значениям разделяем результат?

4. Metrics
   Что считаем внутри каждой группы?

5. Time grain
   Как округляем временное измерение, если оно используется?

6. Row limit
   Сколько строк результата разрешаем вернуть?

7. Create chart
   Для нового несохранённого Chart выполняем текущую конфигурацию.
```

Для нашего основного примера:

```text
Dataset    = sales
Filters    = нет активных
Dimensions = region
Metrics    = SUM(revenue)
Row limit  = 100
```

Результат:

```text
Север 1360
Юг    2645
```

## Почему кнопку нужно нажимать повторно

Изменение параметра в панели управления ещё не означает, что результат уже пересчитан.

После изменения:

- `Dimensions`;
- `Metrics`;
- `Filters`;
- `Time grain`;
- других параметров запроса

снова выполняйте текущую конфигурацию кнопкой:

```text
Create chart
```

Только после этого сравнивайте результат с ожидаемым.

Когда позднее вы будете редактировать уже сохранённый Chart, на этом же месте вместо `Create chart` увидите:

```text
Update chart
```

```text
Dimensions = region
```

Если `Dimensions` пусто, `SUM(revenue)` считается по всему набору целиком.

### Получаются две строки, но числа не 1360 и 2645

Проверьте одновременно:

```text
Metrics    = SUM(revenue)
Dimensions = region
Filters    = нет активных ограничений
```

Также убедитесь, что используется Dataset `sales` из:

```text
Training PostgreSQL → training → sales
```

### После фильтра остался только один регион

Это нормально, если фильтр `region` всё ещё активен.

Удалите фильтр или очистите его значение и снова выполните запрос.

### sale_date нельзя использовать как временное поле

Вернитесь к настройкам Dataset из урока 04 и проверьте, что `sale_date` распознан как temporal/date column.

При необходимости на вкладке `Columns` выполните при закрытом замке `Source`:

```text
Sync columns from source
```

и снова откройте Explore.

### Time grain не появился или ничего не меняет

`Time grain` имеет смысл тогда, когда временной столбец реально участвует в запросе как временное измерение.

Для проверки используйте `Table`:

```text
Dimensions = sale_date
Time grain = Month
Metrics    = SUM(revenue)
```

Если `Dimensions = region`, изменение временной гранулярности само по себе не должно создавать месячные группы.

```text
sales

результат
```

И самостоятельно получить минимум три контрольных результата:

```text
выручка всего = 4005.00

по регионам:
Север = 1360.00
Юг    = 2645.00

по месяцам:
2026-01 = 1160.00
2026-02 = 1180.00
2026-03 = 1665.00
```

Главный навык урока — не запомнить расположение кнопок, а понимать связь:

```text
фильтр → измерение → расчёт → результат
```

## Следующий урок

Сейчас `SUM(revenue)` существует только как разовый расчёт внутри Explore.

В следующем уроке разберём два разных уровня вычислений:

```text
Calculated Column
└── расчёт для каждой строки

Metric
└── агрегированный расчёт по набору строк
```

На учебных данных создадим строковую прибыль:

```text
revenue - cost
```

и агрегированную прибыль:

```text
SUM(revenue) - SUM(cost)
```
