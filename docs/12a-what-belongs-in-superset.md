# Шпаргалка к уроку 12. Где заканчивается Superset

Эта страница — **итоговая памятка**, а не новая глава.

Подробно границы применения Superset уже разобраны в [уроке 01](01-what-is-superset.md). Здесь нужно только проверить, что после практики 02–11 эта модель стала понятной.

## Самая короткая матрица

| Задача | Где ей обычно место |
|---|---|
| Dashboard, KPI, графики (`Chart`) | Superset |
| интерактивная фильтрация | Superset |
| исследование Dataset | Explore |
| повторно используемый агрегированный показатель | Metric |
| простой атрибут строки | Calculated Column |
| SQL-проверка и исследование | SQL Lab |
| локальная SQL-подготовка набора | Virtual Dataset |
| тяжёлая общая витрина | БД / DWH / ETL/ELT |
| регулярная очистка сырых данных | ETL/ELT / БД / код |
| ввод и исправление рабочих записей | операционное приложение |
| согласование и управление процессом | специализированная система |
| сложная статистика / ML | Python / R / специализированный стек |
| ячеечная расчётная модель | Excel / другой расчётный инструмент |
| печатная форма с жёстким макетом | специализированная отчётность |

## 1. Нативная территория Superset

```text
готовые аналитические данные
        ↓
Dataset
        ↓
Explore
        ↓
Metrics / Filters
        ↓
Charts
        ↓
Dashboard
```

Если задача звучит:

> как отфильтровать, посчитать, сравнить и показать уже доступные данные?

Superset обычно подходит хорошо.

## 2. Когда нужен SQL внутри Superset

Нормальные сценарии:

```text
проверить расчёт в SQL Lab
подготовить локальный SQL-набор
сохранить его как Virtual Dataset
```

Сам факт длинного SQL не делает решение неправильным.

Вопрос другой:

```text
где эта логика должна жить постоянно?
```

## 3. Когда логика должна уйти ниже

Если преобразование:

- тяжёлое;
- используется многими Dashboard;
- требуется другим системам;
- должно централизованно контролироваться;
- материализуется заранее;
- является общей бизнес-моделью данных;

лучше рассмотреть:

```text
VIEW
MATERIALIZED VIEW
таблицу-витрину
DWH
ETL / ELT
```

и подключить результат к Superset как обычный источник.

## 4. Что Superset не должен подменять

### Систему ввода данных

Dashboard может найти неправильную строку, но обычный BI-сценарий не предполагает, что пользователь редактирует рабочую запись прямо в графике.

### Согласование и управление задачами

Superset может показать:

```text
сколько задач открыто
сколько просрочено
как менялись статусы
```

но назначение исполнителей, согласование и жизненный цикл кейса — задача другой системы.

### ETL

Superset читает аналитические данные и отправляет SQL источнику. Он не должен становиться конвейером регулярной очистки и загрузки сырых данных.

### Python / R

Наличие статистических визуализаций не превращает Superset в полноценную среду машинного обучения или научных вычислений.

## 5. Где должен жить расчёт

```text
значение одной строки
→ Calculated Column

показатель группы
→ Metric

локальная структура аналитического набора
→ SQL / Virtual Dataset

общая тяжёлая модель данных
→ БД / DWH / ETL

научный алгоритм
→ Python / R / специализированный инструмент
```

Подробнее:

→ [Calculated Column, Metric или SQL?](06b-calculated-column-metric-or-sql.md)

## 6. Контрольные вопросы после курса

Для любого реального Dashboard вы должны уметь ответить:

```text
Откуда пришли данные?
Что означает одна строка Dataset?
Где определён каждый важный KPI?
Какие фильтры меняют результат?
Где выполняется тяжёлая подготовка?
Почему эта логика находится именно на этом уровне?
```

Если ответ:

> «где-то внутри нескольких графиков лежит разный SQL»

архитектуру стоит пересмотреть.

## Главное

```text
Superset
→ исследует, считает и показывает аналитические данные

слой данных
→ готовит устойчивую модель

операционные приложения
→ создают и изменяют бизнес-данные
```

Это не жёсткий технический запрет, а рабочая граница ответственности.
