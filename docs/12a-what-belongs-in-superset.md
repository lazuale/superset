# Шпаргалка к уроку 12. Что делать в Superset, а что вне него

Эта шпаргалка отвечает на вопрос:

> **подходит ли Apache Superset для моей задачи, или я уже пытаюсь использовать BI-систему не по назначению?**

Superset — сильный инструмент аналитики и визуализации данных. Но он не должен заменять одновременно базу данных, ETL, Excel, Python, систему ввода данных и workflow.

Главное правило:

```text
данные подготовлены и нужно их исследовать, считать, фильтровать и показывать
→ Superset подходит

данные сначала нужно тяжело собрать, очистить, исправить или записать обратно
→ скорее нужен другой слой
```

---

## Самая короткая матрица

| Задача | Где логичнее делать |
|---|---|
| Dashboard | Superset |
| KPI | Superset |
| интерактивные Chart | Superset |
| фильтрация Dashboard | Superset |
| SQL-проверка и исследование | SQL Lab |
| простая агрегированная формула | Metric |
| простой расчёт на уровне строки | Calculated Column |
| SQL-подготовка аналитического набора | Virtual Dataset |
| тяжёлая общая витрина | PostgreSQL / DWH / ETL/ELT |
| сложный JOIN многих источников для всей компании | чаще слой данных, а не отдельный Chart |
| регулярная очистка грязных данных | ETL/ELT / БД / код |
| изменение исходных строк пользователем | не Superset |
| форма ввода | не Superset |
| согласование / workflow | не Superset |
| сложная статистика / ML | чаще Python / R / специализированный стек |
| ячеечная модель как в Excel | Excel / другой расчётный инструмент |
| pixel-perfect печатная форма | обычно специализированная отчётность |

---

# 1. Нативная территория Superset

Superset особенно хорошо подходит, когда нужно:

```text
подключиться к аналитическому источнику
        ↓
получить Dataset
        ↓
посчитать Metrics
        ↓
исследовать данные в Explore
        ↓
построить Charts
        ↓
собрать Dashboard
        ↓
дать пользователю фильтры
```

Это основной рабочий контур продукта.

---

## Dashboard и KPI

Примеры нормальных задач:

```text
выручка за период
количество документов
доля ошибок
динамика по дням
сравнение участков
распределение по категориям
таблица проблемных объектов
```

Для такого сценария Superset подходит нативно.

---

# 2. Explore — аналитика без написания SQL на каждый Chart

Если Dataset уже имеет правильную структуру, пользователь может задавать:

```text
Dimensions
Metrics
Filters
Time range
Time grain
```

и получать новые аналитические срезы без отдельного SQL-запроса для каждого графика.

Это одна из ключевых сильных сторон Superset.

---

# 3. Metric — место для повторно используемого показателя

Например:

```sql
SUM(revenue) - SUM(cost)
```

Если показатель должен одинаково использоваться на нескольких Chart одного Dataset, сохранённая Metric — нормальное место для его определения.

Но Metric не должна превращаться в огромную скрытую программу подготовки данных.

Если формула требует изменения структуры набора данных, нескольких JOIN или сложной последовательности преобразований, уровень задачи уже другой.

---

# 4. Calculated Column — простая логика строки

Например:

```sql
revenue - cost
```

или:

```sql
CASE
    WHEN revenue >= 500 THEN 'Крупная'
    ELSE 'Обычная'
END
```

Это удобно, когда Dataset уже правильный, а нужно добавить небольшой вычисляемый атрибут.

Не надо создавать Virtual Dataset только ради одной простой построчной формулы.

---

# 5. Virtual Dataset — полезный промежуточный слой

Virtual Dataset подходит, когда SQL должен сформировать удобный аналитический набор:

```text
выбрать нужные поля
переименовать поля
добавить SQL-выражения
соединить несколько таблиц
сделать CTE
использовать оконную функцию
ограничить исходный набор данных
```

Но Virtual Dataset всё равно остаётся SQL, который выполняется источником данных.

Он не превращает тяжёлый запрос в заранее рассчитанную таблицу автоматически.

---

# 6. Когда SQL лучше вынести из Superset в базу

Если одна и та же логика:

- нужна многим Dashboard;
- используется не только Superset;
- тяжёлая по вычислениям;
- должна централизованно контролироваться;
- должна материализоваться заранее;
- является частью корпоративной модели данных;

то разумнее рассмотреть:

```text
VIEW
Materialized View
таблицу-витрину
DWH-модель
ETL/ELT
```

Упрощённо:

```text
локальная аналитическая подготовка
→ Virtual Dataset

общая корпоративная модель
→ слой данных
```

---

# 7. Superset не является ETL-системой

ETL/ELT решает задачи вроде:

```text
забрать данные из нескольких систем
очистить
нормализовать
сопоставить справочники
исправить типы
дедуплицировать
рассчитать тяжёлые промежуточные таблицы
сохранить результат
```

Superset может читать результат такой подготовки.

Но строить всю инженерную цепочку загрузки данных внутри Dashboard — плохая архитектура.

---

# 8. Superset не является системой ввода данных

Типичная неправильная постановка:

> пользователь увидел ошибку на Dashboard и должен прямо здесь исправить строку в PostgreSQL.

Базовый сценарий Superset — чтение и анализ.

Для ввода и редактирования записей нужны другие приложения или специальные операционные интерфейсы.

Dashboard может помочь **найти** проблему, но не обязан быть местом её исправления.

---

# 9. Superset не является workflow-системой

Задачи вида:

```text
назначить исполнителя
изменить статус заявки
согласовать документ
оставить обязательный комментарий
вести жизненный цикл кейса
```

относятся к системам задач, workflow, BPM или специализированным приложениям.

Superset может показать аналитику по такому процессу:

```text
сколько заявок открыто
сколько просрочено
среднее время выполнения
воронка по статусам
```

Но сам процесс лучше вести в системе, для этого предназначенной.

---

# 10. Superset не является Excel

Excel хорош там, где пользователь работает с ячейками, вручную вводит значения, строит индивидуальные расчётные модели и меняет структуру файла по ходу работы.

Superset мыслит иначе:

```text
Dataset
→ Dimensions
→ Metrics
→ Filters
→ Chart
```

Если задача звучит:

> пользователь должен вписать значение в B17, протянуть формулу и вручную поправить несколько строк,

это не естественный сценарий Superset.

---

# 11. Superset не является Python/R-средой анализа

В Superset есть отдельные статистические визуализации, но это не означает, что платформа должна заменить полноценную аналитическую среду.

Для задач вроде:

```text
машинное обучение
сложное моделирование
кластеризация
нестандартные статистические тесты
оптимизация
simulation
сложная обработка массивов
```

обычно удобнее Python, R или специализированная система.

Результат такого анализа затем можно положить в БД и визуализировать в Superset.

---

# 12. Сложные расчёты: где граница

Не сложность формулы сама по себе определяет место расчёта.

Нужно смотреть на уровень логики.

```text
атрибут одной строки
→ Calculated Column

показатель группы
→ Metric

структура аналитического набора
→ SQL / Virtual Dataset

тяжёлая повторно используемая подготовка
→ БД / DWH / ETL/ELT

научный алгоритм
→ Python / R / другой аналитический стек
```

→ [Calculated Column, Metric или SQL?](06b-calculated-column-metric-or-sql.md)

---

# 13. JOIN: Superset может, но это не значит «всё тащим внутрь»

Virtual Dataset позволяет написать SQL с JOIN.

Это нормально для локальной аналитической задачи.

Но если один JOIN:

- используется десятками Dashboard;
- связывает центральные справочники;
- содержит сложные правила дедупликации;
- должен иметь единое контролируемое определение;

лучше рассмотреть централизованный объект в слое данных.

Особенно важно не забывать о зерне.

→ [JOIN и зерно данных](06c-join-and-data-grain.md)

---

# 14. Большие объёмы данных

Superset не обязан загружать весь Dataset в браузер.

Агрегации и фильтрация обычно выполняются в подключённой СУБД.

Поэтому производительность Dashboard зависит не только от Superset, но и от:

```text
структуры таблиц
индексов
партиционирования
SQL
объёма сканирования
мощности СУБД
кэширования
числа одновременных запросов
```

Если запрос к источнику сам выполняется минуты, смена цвета Chart проблему не решит.

---

# 15. «Можно сделать» и «стоит делать» — разные вопросы

В BI часто можно технически собрать сложную конструкцию внутри одного Virtual Dataset.

Но архитектурный вопрос другой:

> будет ли это понятно, проверяемо, повторно используемо и поддерживаемо через полгода?

Если нет — логика находится слишком высоко в стеке.

---

# 16. Простая схема выбора инструмента

```text
Нужно показать и исследовать данные?
→ Superset

Нужно определить KPI?
→ Metric

Нужно добавить простой атрибут строки?
→ Calculated Column

Нужно локально подготовить SQL-набор для анализа?
→ Virtual Dataset

Нужно регулярно готовить общую витрину?
→ БД / DWH / ETL/ELT

Нужно вводить или исправлять данные?
→ операционное приложение

Нужно управлять задачами и статусами?
→ workflow / task management

Нужна сложная статистика или ML?
→ Python / R / специализированный инструмент
```

---

# 17. Пример нормальной архитектуры

```text
Операционные системы
        ↓
ETL / ELT
        ↓
PostgreSQL / DWH
        ↓
аналитические таблицы / views / витрины
        ↓
Superset Dataset
        ↓
Metrics
        ↓
Charts
        ↓
Dashboard
```

Superset находится ближе к пользователю и потреблению аналитики, а не обязан закрывать весь путь от сырой транзакции до бизнес-процесса.

---

# 18. Пример плохой архитектуры

```text
сырые таблицы из пяти систем
        ↓
огромный SQL на сотни строк в каждом отдельном Chart
        ↓
разные копии одной формулы
        ↓
разные JOIN
        ↓
разные результаты одного KPI
```

Такой Dashboard может работать технически, но поддерживать его будет тяжело.

---

# 19. Хороший критерий

Для каждого Dashboard должно быть возможно ответить:

```text
откуда пришли данные?
что означает одна строка Dataset?
где определён каждый важный KPI?
какие Filters меняют результат?
какой слой отвечает за подготовку данных?
```

Если ответ:

> «где-то внутри нескольких Chart есть разный SQL»,

архитектуру стоит упростить.

---

# 20. Главное правило

```text
Superset
→ анализирует и показывает подготовленные аналитические данные

БД / DWH / ETL
→ формируют устойчивый слой данных

операционные системы
→ создают и изменяют бизнес-данные

Python / R
→ решают специализированные аналитические задачи
```

Границы не абсолютно жёсткие, но эта модель помогает не превращать Superset в универсальный комбайн.
